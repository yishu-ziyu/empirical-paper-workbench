# Phase P2 首页渐进披露 BDD

目标：把首页从“细节堆叠”改成“先给决策信号，再按需展开证据”。首屏只显示用户下一步需要判断的信息，技术细节、审计边界和执行分工默认折叠，避免冲击短时记忆。

## 行为 1：智能中控默认只显示状态摘要

Given 用户打开研究工作台首页
When 系统已经读取 workflow contract 的 `intelligence_layer`
Then 首页应直接显示本地 Codex Supervisor 是否启用、证据等级和阻塞数量
And Provider 版本、执行开关、完整阻塞原因和派工计划必须放在可展开详情里

业务规则：智能中控是“是否可以进入大模型派工”的信号，不应该默认把所有后端字段摊给用户。

## 行为 2：用户可以按需展开智能中控细节

Given 智能中控摘要已经显示
When 用户点击“查看中控详情”
Then 页面应展开 Provider、允许执行、版本、阻塞项和派工计划
And 这些信息仍保留证据等级和本地执行边界

业务规则：细节不是删除，而是延后展示；用户需要审计时可以一键展开。

## 行为 3：SupervisorPlan 默认只显示审阅状态和主操作

Given 用户打开首页的 SupervisorPlan 审阅台
When 计划为空或处于待审阅状态
Then 页面应直接显示当前状态、下一步主按钮和人工确认边界
And 版本、写入边界、阶段计划、子 Agent 分工、证据要求和风险必须默认折叠

业务规则：SupervisorPlan 的核心是“先审阅再执行”，首屏不应该用长列表淹没这个主动作。

## 行为 4：详情控件必须支持键盘和辅助技术

Given 详情内容默认折叠
When 用户通过鼠标或键盘触发详情摘要
Then 页面应使用原生 `details/summary` 或等价可访问结构
And 初始状态不得默认 `open`

业务规则：渐进披露不是纯视觉效果，必须让键盘用户和屏幕阅读器也能理解“可展开/已展开”的状态。

## 边界条件

- 这次不改变 `/supervisor-plan` API，也不启用真实 Codex 执行。
- 这次不改写变量角色、DesignSpec 或 RunPlan。
- 这次只整理首页中控与 SupervisorPlan 的信息密度；其它页面继续沿用现有 clean workbench 规则逐步收敛。
