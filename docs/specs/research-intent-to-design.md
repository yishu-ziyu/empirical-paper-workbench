# 从研究意图到可执行设计

日期：2026-09-17。
状态：**产品顺序已由用户确认；本文件给出下一批实施方案，尚未实现或验收。**
相关：[首批独立评审](../reviews/20260917-formal-confirmation-chain-independent-review.md)、[核心产品契约](../product/core-product-contract.md)。

## 1. 本次改变与不变的内容

新顺序：**明确想弄清什么 → 检查已有或候选数据 → 形成可执行研究设计 → 用户确认 → 执行并审阅证据。**

这项决定替代 `infer-design-contract.md` 中“先确认设计才能进入数据候选/挂接”的顺序要求。题目整理正确不等于设计已确认；上传、读取元数据、检查可行性不以设计已确认为前提。

仍然保留：数据采用须明确；正式估计前有当前版本的设计、样本与具体设定确认；逐动作消费 #40 许可；不伪造结果、引用或批准；历史记录保留。七类业务对象不是七个固定页面，流程允许返回。

用户希望知道教育本身是否提高工资时，系统保留这个问题，不擅自改成“只研究相关”。实际比较路径、关键假设与已经得到的证据分别保存，不相互冒充。
也不把所有限制一律拖到结果后才说：发现真实缺列、不可用方法或需要用户取舍的条件时，当场说明发现、依据与可行的下一动作。

## 2. 为什么这样选：调研事实与产品推论分开

| 方案 | 优点 | 代价 / 本项目的问题 | 本轮处理 |
|---|---|---|---|
| 先填技术设定并锁定，再寻找数据 | 流程容易实现，执行规则明确 | 尚不了解数据时容易锁定空变量或错误样本；用户批准的可能只是模型猜测 | 不再作为默认入口 |
| 一直聊天，Agent 随时自行改方案、试算 | 对话自由，探索阻力小 | 用户难以知道哪版问题、数据和设定产生了结果；批准与历史可能漂移 | 保留自然语言入口，不采用隐式批准 |
| 意图先行，检查材料后提出方案，明确批准当前版本 | 用户能在具体事实基础上做选择，保留可修改和可追溯性 | 需要可行性检查、版本绑定和可靠恢复；不能只加几句提示词 | 采用此方向；复用现有后端能力逐批落实 |

调研事实：Elicit 官方 Paper Search 展示了问题澄清、可编辑筛选标准和纳入/排除理由。[来源：Elicit Paper Search](https://elicit.com/solutions/search)。这里借鉴的是“判断可修改且有依据”，不是将文献筛选顺序直接当作实证研究流程的证明。

方法依据：World Bank DIME 将预分析计划的目的指向减少数据挖掘和规格搜索，也指出完全预先规定可能限制探索；COS 区分计划内与探索性分析，特别提醒已有数据和已观察结果会影响分析决策。[DIME](https://dimewiki.worldbank.org/Pre-Analysis_Plan)、[COS](https://www.cos.io/initiatives/prereg)。

**本产品的推论**：允许检查数据和迭代方案，同时保留先前做过/看过的分析记录。不把“点击确认之前暂时不显示系数”包装成防偏差保证，也不把应用内确认叫正式预注册。元数据核对、描述统计、探索试算的作用不同；如果已经做了后两者，记录实际发生的时间、目的和产物，不事后改写成未看数据的计划。

## 3. 用户实际经历什么

### 3.1 收到想法后先做什么

用户：“我想研究教育是否提高工资。”

系统先检查上下文：已有文件、明确的人群/时间、先前回答是什么。若已有文件，直接进入获准的结构检查；不要再问“你有没有数据”。没有文件和数据线索时，可问“你手上已有数据，还是先一起找？”。这不是每次固定必问的一句话。

需要澄清时，一次问一个会改变行动的问题，并说明其用途。例如“这里的工资指月工资还是全年劳动收入？这会决定用哪一列。”文件中的标签已能可靠回答时，先引用标签，不让用户重复填。

尚不明确的概念可以作为待澄清事项保存。不能为了填满字段，将用户没说的国家、人群、政策年份、变量定义自动变为确认事实。

### 3.2 用户已有数据

在同一研究会话接入文件，检查文件格式、字段标签/单位、时间与观察单位、缺失和可用数据范围。产出简短的事实说明及必要的澄清，例如：

> 文件里有教育年限、月工资和地区。工资列的说明是“税前月工资”。我先按这一口径整理比较方案；“就业状态”这一列的编码还需要核对。

这是示例，不是通用固定文案。每个事实必须能回到文件元数据或实际检查；缺编码说明不能仅根据列名猜测。是否检查分布、试算或改变样本由实际任务决定并留痕。

候选数据可浏览不等于已采用。选择当前文件用于研究时记录挂接确认；失败就保留候选和输入，不显示“已采用”。更换文件从当前会话创建新候选版本，不丢掉研究问题，也不沿用旧文件的批准。

### 3.3 用户没有数据

先保存研究意图和必要的数据需求，再查可用来源；不为了解锁搜索而伪造已确认设计。能检索到的展示来源与匹配依据，尚未接入的检索能力不装成能用。

已有 `find-data` / classic-5 依赖 confirmed design 的端点要区分“意图驱动的候选搜索”和“对已确认方案的匹配”，不得删除全部门槛或伪造 confirmed 来复用旧接口。
本批优先完成自带数据路径；无数据路径完成意图保存、返回继续、已有候选入口的正确语义，不在同一批扩展所有外部数据连接器。

### 3.4 什么时候提出研究方案

已有足够事实说明研究对象、关注的结果、比较方式、数据如何落实时，提出方案；不能因为对话满两轮就自动当作齐全。缺口会影响比较或执行时继续核查/澄清；不影响当前行动的细节后置。

展示重点随问题而定，不冻结为“三块信息”模板。用户能看见本次会做的比较、采用的数据和样本、尚需决定的选择，并直接修改。方法、变量映射、公式和检查依据可展开查看，但不能隐藏将要改变研究含义的内容。

用户修改“只研究初入职场的人”时，更新的是研究范围；系统指出目前能否从真实字段定义该范围，缺毕业时间不能用年龄偷偷替代。自然语言修改和局部编辑写同一份草稿。

### 3.5 确认到底产生什么

设计确认批准的是一份可执行方案的**具体版本**，绑定所用数据和变量/样本映射，不是方法有效性的证明。
样本描述和执行设定仍需各自确认真实对象；本批不自动把它们设 true，也不合并成无法区分的万能“继续”。可以在同一个审阅过程完成，不要求新建多个页面。

在数据检查后才确认设计，必须同时拆掉“生成预览要先确认设计、确认设计又要先看预览”的循环：允许对草稿进行只读可行性/预览生成，正式估计仍在批准之后。
关键设计改动生成新草稿并解释差异；旧版保留可查。先前的结果、结论和批准不能自动适用于新版。

## 4. 全栈实施边界

| 层 | 复用与调整 | 必须验证 |
|---|---|---|
| 入口 / 会话 | 复用 `DeskPage`、`POST /sessions` 和现有 SessionStore。先持久化意图，不在空桌“理解正确”回调中自动提出并确认执行方案 | 无设计也能恢复问题、继续上传；确认失败不会切到假成功界面 |
| 研究意图 | 先核对现有 `research.question` / 方向对象是否能在无数据、非教学会话独立承载；不足时在同一 session 中增加最小 `research_intent`，含用户原话、当前理解、约束和待澄清项及版本 | 不从 Card 模板借值；不新建第二套存储或全局 stage |
| 数据与可行性 | 复用 attach、ingest、metadata/EDA；为新正式会话明确类别，不能由字段缺失推断 legacy。检查接口接受未确认设计或无设计 | 数据接入前后 session 不变；输入版本、检查依据明确；正式估计门不下沉到文件检查 |
| 设计提出 / 编辑 | 复用 `session.design`。提出器获得意图及去敏数据描述/检查结果；现有题目规则只能作候选，不把某几个关键词直接当通用变量映射 | 变量来自实际 schema，语义映射有依据；局部编辑可保存，模型建议不能自己确认 |
| 确认 / 运行 | 在既有 confirm/RunRepository 内增加版本校验和原子前置检查。确认和运行分别记录 design/data/spec/preview 标识；执行 payload 从批准版本生成 | 多窗口编辑冲突返回明确冲突；不能锁 age 却执行 schooling；同意图幂等不创建第二个 run |
| 当前状态展示 | 复用 snapshot 与带 run 所有权的观察；将本批新增确认命令收束为有统一过期/错误处理的模块，不继续复制 workspace 分支 | 主区域、侧栏、底栏对待确认/运行/失败说同一件事；每个 await 后核对归属 |
| 诊断与采用 | 保留 #40 三档许可。可行性、核查执行、风险发现、证据支持、用户批准分别表达 | 未知不等于通过；有 confirm 才要求针对该风险的决定；因果目标不等于因果结论 |

API 的精确字段和新端点名由执行者先列出最小变更表，复用能表达同一语义的现有服务；不能只改前端文字。类型变更经既有生成流程同步，不手写覆盖生成文件。

确认请求至少携带所见对象的版本；服务端读当前版本并在同一事务验证、确认/入队。POST 成功响应可表达当次接受事实，当前界面仍要按后续 snapshot 版本对齐；响应丢失先核对，不擅自说成功或换新意图再投。
`research_direction` 与 `main_specification` 是已批准设计的执行投影。给执行表单播种一次不等于已经约束它，服务端必须检查差异或要求修订。

## 5. 修改影响表

| 修改 | 需要重新核对 | 不应发生 |
|---|---|---|
| 只改显示标题、界面语言、排版 | 显示内容；问题含义未变时不动执行版本 | 全部重算、撤销数据采用 |
| 改研究对象/结果定义/比较逻辑 | 意图、对应设计、具体设定及依赖结果 | 偷换变量、旧结果继续标为当前已批准 |
| 更换数据或改变清洗/筛样本规则 | 数据版本、挂接、可行性、样本/设定、相关诊断与结果 | 清空全部历史；用旧 Table 1 确认新数据 |
| 仅提出替代设计/探索试算 | 草稿/探索记录；只有明确采用才变主分析 | 预览自动覆盖主结果；事后抹去探索记录 |
| 旧任务完成 / 旧请求返回 | 写入其自身版本的历史；仍是当前版本才更新当前展示 | 按 session 相同就把旧结果发布成当前结果 |

失效针对真实依赖，不针对任意一次对象写入。先复用已有 evidence revision / stale 机制；缺少的数据与设计版本用最小字段补齐，不能用一串无归属布尔值代替绑定。

## 6. 执行顺序与任务切片

**第一批：修复交付完整性，`FORMAL-CONFIRMATION-CHAIN-2`。** 以独立评审为可执行问题清单，先处理 R7 测试环境，再处理 R1–R6、R8 和幂等/响应丢失补证。此批修正确认约束，不新增“数据检查前必须确认设计”的硬限制。修复后独立 review，通过后再进入下一批。

R7 最小边界：显式 mock 覆盖所有节点/子进程/reload 且不加载真实凭据，测试阻止外部连接；不修改用户全局密钥文件。基线重新按源码 allowlist 采集。发现已有敏感副本时停止传播，列明仅待清理的副本路径；清理需确认范围，禁止删除原配置或原研究文件。不得在修复 mock 之前用真实 key 验证。

**第二批：意图优先的可见闭环，`INTENT-TO-DESIGN-1`。** 从无设计的新正式会话出发，输入问题、接入同会话 CSV、检查真实字段与样本条件、修改并确认可执行方案、完成样本/设定确认、产生一条真实估计。用最小呈现验证这一循环，不重做全站布局或新增代理框架。

交付时提供两个对比场景：①问题清楚且数据充分，不重复追问；②已有文件但字段含义不清，提出具体澄清而不是直接降级研究目标。页面形式和文案示例以这两个场景的实际可用性检验，不因本文件用了某种段落结构就照搬成固定组件。

**第三批，单独开任务：** 普通数据的证据采用、结论与章节失效传播、文稿/代码一致性。不能把第一批确认链修复说成完成这一批，也不因后续待做而推迟首批已发现错误。

## 7. 第二批的验收场景

| 编号 | 输入或动作 | 可观察结果 |
|---|---|---|
| I1 | 无文件输入一个明确研究问题，刷新 | 意图保留；没有自动 confirmed design 或默认采用的数据 |
| I2 | 未提出设计就上传数据 / 先上传再说明问题 | 同一会话检查可进行；不会因 hasDesign=false 调 `/upload` 建新研究而丢意图 |
| I3 | 输入已给出人群、时间和数据位置 | 不重复问已知信息；引用实际上下文，推进检查 |
| I4 | 文件含近似字段但语义不符，如家庭收入与个人工资 | 标出实际定义并询问/找资料，不把字符串相似当已确认映射 |
| I5 | 信息充分 vs 一项决定性歧义 | 充分时提出可执行方案；歧义时一次一个有行动后果的问题，无固定轮数自动确认 |
| I6 | 修改人群、结果定义、比较方式 | 编辑写入当前草稿；提交确认的正是用户所见版本，旧版历史可回查 |
| I7 | 缺设计/挂接/样本/具体设定确认，直接调用正式估计 | 服务端拒绝；但可行性检查仍可用，避免把执行门当查看门 |
| I8 | 两个窗口编辑；旧 preview/确认/终态在变更后到达 | 返回冲突或归入旧版历史，不污染当前；纯 UI 语言切换不失效研究 |
| I9 | 200 确认已落库但响应丢失；202 已入队但响应丢失 | 先核对并用原意图接回，不造批准、不重复运行 |
| I10 | unknown / allow / confirm / forbid | 文案与可用动作分别准确；没有早期通用免责，也没有未知宣称通过；风险决定有版本绑定的留痕 |
| I11 | 已做描述统计/探索后再确认方案 | 先前记录不消失；不把确认包装成未受数据影响的预注册 |
| I12 | 两份非 Card schema、桌面与小屏完整操作 | 均能通过可见动作走到正确设定和真实统计；截图/请求/运行工件/独立复算互相对应 |

故障测试可以模拟事件与模型，但不能模拟被验收的批准/估计服务而宣称业务闭环成立。获准真实数据可用则验证真实数据；否则明确标为合成接线与数值验收。
模型理解质量另用输入/期望行为集评价；mock 通过不证明模型理解正确。真实模型评测必须单独获模型/账户/预算授权；没有授权仍完成可做的契约与统计验证。

首批修复仍以原 C1–C12 中的正确性要求和新反例为回归，取消的旧页面顺序不再作为第二批验收标准。卡住必须给具体证据与最小缺口，不可擅改验收条款。

## 8. 接力纪律

执行者每批先保存当前源码基线和 hash（含继承未提交改动，排除环境与数据），交付包含所有新增文件内容的增量及最终指纹；评审对象停止变化后再 review。
保持当前 checkout 串行接力。除非用户另行授权，不 commit/push/merge/rebase/部署，不装依赖，不委派模型，不读取或复制真实凭据。
改动、验收、剩余项写入该批独立任务文件与索引；不把旧评审记录改写成新代码已通过。具体实现继续由执行 Agent 完成，本轮只作独立评审和规格整理。
