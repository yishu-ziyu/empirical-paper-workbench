## 三、解法方向（代价摆清，不排序——按奕枢规矩，排序是他的事）

### 方向 A：先钉定位，再动代码

- **做什么**：写一篇 ADR-0012，显式 supersede ADR-0010 的"研究者"框定与 08-18 devlog 的"课设"定位，声明唯一用户；并仲裁"替你干完"与"硬证据门"的冲突。
- **架构冲击**：0。
- **开发量**：≈0（一天以内）。
- **UX 改变**：0。
- **代价**：必须由奕枢本人拍板，团队无法代劳。且一旦拍板，必然要砍掉一批已建成功能。
- **不做它的代价**：后续每一周都在随机 cement 三种定位中的一种。这是唯一一条"现在不做就持续变贵"的动作。

**完整时间线：**


**结论：不是"13 天漂移留下三层化石"，是"一次有意的删除，接着九天后一次无意的重建"。**

这比初稿的"漂移"判断更重：
- **漂移**意味着改主意，至少每次都是当下的决定
- **失忆**意味着 08-18 的教训被执行过（干净卸载），然后在 08-27/29 被彻底遗忘——三套新 UI 建出来时，没有任何一次提交负责确认"08-18 已经删过一次了"

**且 pm 最尖锐的一点成立**：08-27 同一天、同一个北极星（devlog「替你干完」对标 Apodex），在**两个不同 commit** 里产出两套互相矛盾的 UI（右栏 8 个英文节点 vs 中栏 4 步营销文案）。**决策在诞生的当天就没有被翻译一致。**

##### 对第三节措辞的修正

第三节称"定位 13 天三改"。更准确的表述是：

- **决策层面确实是三次**（08-16 / 08-18 / 08-27），这点不变
- **但 UI 层面的三套并存，主因不是决策反复，是 08-27→08-29 的 72 小时并发施工未经对齐**（pm 的措辞，已采纳）

**并且它让方向 A 与方向 B 合并为同一个动作**——此结论不受映射推翻影响，反而被日期证据加强：既然三套活旅程都是这三天的产物，**选定权威旅程即等于宣布哪天的决定算数**。

#### 三个后果

**一、唯一活着的交互式路径就是那串英文标识符（第 2 套）。** 用户被压迫是真的，但压迫源不是"8 站旅程"，是右栏 8 个代码名。

**二、4 步版本已经上线了。** `上传 → 方向 → 估计 → 按章写` 就在工作台头部。团队凭直觉早就知道旅程是 4 步，只是它是纯文案、没接到路径组件上。**本方向 B 提出的 3–4 步不是新想法，是已经写在屏幕上却没实现的东西。**

**三、命名工作已经做完了。** 8 步中文文案（第 3 套）已写好、翻译好，只是挂在未挂载的组件上，可直接复用。

#### 修正后的方向 B

- **做什么**：让右栏（第 2 套）对齐屏幕上已有的那段 4 步文案（第 4 套）；把已写好的中文标签（第 3 套）接上去。
- **架构冲击**：**后端零改动**——节点一个不动；`progress.py` 的 `_JOURNEY_STAGES` 是否同步视定位决定。
- **开发量**：**1–2 天**（初稿估 3–5 天，因命名工作已存在而下调）。
- **UX 改变**：右栏从 8 个代码名变成人话。
- **代价**：牺牲研究者要的逐步控制粒度——依赖方向 A。
- **~~顺带解决第 8 站"降AIGC"空壳~~**：**此条作废**。那套站点本就未渲染。且真实情况更轻——`i18n.tsx:537` step8 已写作 `⑧ 导出`（删了"降AIGC"），`progress.py:47` 仍写"降AIGC导出"。**是改了一半，不是未实现**：文案删了、后端没删，因为没人认领哪套算数。

#### 由此产生的最该递给奕枢的问题

不是"选哪个方向"，而是：

> **四套旅程，哪套算数？**

选择题，不是工程题；对齐成本 1–2 天。但答案取决于"用户是谁"，绕回第三节的定位问题。**四套旅程并存本身就是定位未定的物证**：每做一次定位摇摆就留下一套旅程，没有一套被作废。

### 方向 C：不要把 2–4 周投进识别工作台

- **理由**：它 cement 的是 08-16 定位，而 08-18 否决、08-27 漂移的轨迹都在离开它。在 A 拍板前投入，是拿最大工程量去赌最早的一个答案。
- **若确实要动识别**：先做 pm 提的**失效传播**（`invalidate_downstream`，3–5 天）。这是三个方向里唯一对用户无害、且无论最终定位是哪一种都必须有的。
- **注意**：补平行趋势检验会连带触发星级语义重划（fail 了算 1 星还是 0 星），而 `graph.py:56` 的路由只认 0 星——补检验而不改路由，等于新增的失败仍然不拦人。

用户会以为设定表跑过并据此写稳健性论述，实际什么都没跑。

#### 同模式还有两处，方向相反

**`translate_code` / `export_docx` 永远不可能 completed**（`paperPath.ts:93-94`）：

```ts
const translate: PathStatus = state.canExport ? 'active' : 'pending'
const exportDoc: PathStatus = state.canExport ? 'active' : 'pending'
```

两者同源于 `canExport`，而 `canExport = writtenChapters.some((ch) => Boolean(ch.content))`——即"有任意一章写过内容"，**与实际导出无关**。用户导完 PDF/Word 后，最后两站永久停在"进行中"。

一处**谎报完成**，两处**永不承认完成**，同源：状态由代理信号推导，不由产物推导。

#### 根因比"代理信号"更深一层：用户可见层是实现的直接投影

`i18n.tsx:181-188`（zh 词典；默认语言为 zh，`getInitialLang` 兜底返回 `'zh'`）：

```
'path.upload_data': 'upload_data'      'path.spec_curve': 'spec_curve'
'path.clean_data': 'clean_data'        'path.generate_outline': 'generate_outline'
'path.set_direction': 'set_direction'  'path.translate_code': 'translate_code'
'path.generate_chapter': 'generate_chapter / approve_chapter'
'path.export_docx': 'export_docx'
```

八站标签**全部是原始代码标识符**。而同一词典里 8 个清洗步骤标签是正常翻译的（`i18n.tsx:190-197`：`profiling · 契约`、`merge · 合并`、`audit · 留痕`）——翻译机制没问题，是路径站点从未被起过产品名。

**结论：8 站不是设计出来的用户旅程，是后端节点名单渲染成了 UI，中间没有产品层。**

这与本文第三节的定位问题**同一个根**：从定位到用户旅程、从节点到标签，**两次翻译都没有人做**。

**对方向 B 的意义随之改变**：砍站不只是给用户减负，是补做一次从未做过的产品翻译。B 的性质是"把后端节点名单换成用户旅程"，不是"删功能"。

**面试副作用**：截图里出现 `upload_data`、`spec_curve` 这类标识符，是"工程师做的产品"最直观的物证，比任何答辩说辞都硬。修它是半天工作量，收益在观感。

## 五、一句话结论

工程没问题（1062 测试为证），流程形状也不是主要问题。
**主要问题是：这个产品在 13 天里被定义了三次，而没有任何一次被显式作废。** 在定位被钉死之前，任何流程改造——包括给识别加迭代——都是在给一个未选定的产品加固。

**可验收的判据（四套旅程的发现把它收紧成了一条）**：

> 当产品层存在时，同一个概念只应有一个权威表述。
> 现在"旅程"有四个表述（后端 8 阶段 / 右栏 8 英文节点 / 悬空 8 步中文 / 头部 4 步文案），**四个都不是权威**。

这条判据的价值在于它可自检、可回归——不需要先回答"用户是谁"就能查：任一用户可见概念若在代码里出现两套以上表述，产品层就是缺失的。按这个判据扫一遍，定位漂移留下的痕迹会自己浮出来。

**因此递给奕枢的不是一个方向排序，而是一个选择题**：四套旅程，哪套算数？成本 1–2 天，但答案取决于用户是谁，绕回定位。
