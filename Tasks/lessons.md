# Lessons

## 2026-05-25：新工作台模块必须先有设计契约，再接业务工作流

用户反馈：其他模块的设计要先规范好，规范好之后才能接具体工作；否则旧前端的信息拥挤、解释性文案和功能堆叠会在 React 新入口里复发。

后续规则：

- 每个 React 工作台模块先定义主决策、默认摘要、右侧 Drawer 详情、空态、加载态、错误态和正式层写回边界，再接真实 API。
- 主屏不显示“为了防止风险...”这类解释性防守文案；风险和证据要求放进用户点击后的审阅层。
- 任何高噪声信息，包括日志、JSON、权限、成本、证据明细、Agent 工具调用，都默认进入右侧 Drawer 或折叠详情。
- 设计契约必须能被测试锁住；不能只靠口头审美判断。

## 2026-05-25：本地 Auto Mode 不能 fallback-first，必须 best-available-first

用户反馈：既然目标是最好的本地科研 OS，就不能默认做一个保守 dry-run 或半吊子候选层，然后停下来解释风险。

后续规则：

- 本地 CLI / Auto Mode 默认追求当前机器可用的最高能力：StatsPAI、StataMCP、CNKI、Web、Zotero、本地数据、LLM Supervisor、agentmemory 都应被探测或接入。
- 不可用能力必须写入审计状态，说明缺什么、为什么不可用、下一步怎么接入；不能静默跳过。
- 自动产物可以大胆生成草案层，但所有会影响正式研究结论的写回必须经过人工 review。
- 完成后必须同时报告：已经真实跑通的能力、只是探测到但尚未接入的能力、因为安全边界刻意不做的写回。
- 如果全量测试不绿，必须明确说出失败测试属于当前改动、既有漂移还是下一轮前置修复，不能只报目标测试通过。

## 2026-05-25：用户给出明确 UI 原型时，先做原型本身，不要泛化成全局设计

用户反馈：后面不同板块会有不同 UI 偏好，当前发来的 Claude-style 输入器和滑动标签就是先要做的事情；并且第一版基本只想要黑白灰。

后续规则：

- 当用户给出明确 UI 组件代码或截图，并说“这就是我喜欢的设计”，先实现该组件切片，不要先扩展到全局 IA、完整模块重排或其他风格探索。
- 新前端第一阶段不要把所有产品能力铺满；输入器、附件、模式选择和阶段导航应保持强留白和低信息密度。
- 对该用户当前产品，黑白灰是默认安全配色；除非用户另行指定，不用彩色状态色表达 UI 层级。
- 旧前端只有在新 React 入口被用户认可后再删除，避免同时丢失可用回退面。
- 首屏不要放“我们现在只验证…”、“不展开…”、“不会静默…”这类防守性说明；这些边界应放到具体审阅、提交、写回动作的确认层里。
- 黑白灰不等于纯黑纯白；用户当前偏好是低对比、干净、未来感，强对比需要主动下调。

## 2026-05-13：任务收尾说明必须产品化

用户反馈：每次完成任务后，如果只解释代码、测试和内部状态，会跟不上当前产品开发进度。

后续规则：

- 每次完成一轮开发，先用产品语言说明“这轮对用户体验/产品流程改变了什么”。
- 必须明确页面入口：用户打开哪个 URL、点击哪个导航、看哪个面板、哪个按钮能验证。
- 剩余风险要写成产品风险，而不只是工程风险。例如“还不能写回正文”“还没有 docx 导出预检”“本地验收产物未决定是否进入 fixture”。
- 下一步计划要说明为什么是下一步，以及它在研究生命周期中的位置。
- 技术细节、测试命令和文件路径放在后面，作为证据，不作为唯一汇报主体。

推荐收尾结构：

1. 产品进展：这轮让用户现在可以做什么。
2. 你可以怎么验收：页面入口、点击路径、应看到的状态。
3. 行为覆盖：对应 BDD 行为。
4. 测试覆盖：命令和结果。
5. 实现范围：关键文件和接口。
6. 剩余风险：产品风险优先，工程风险其次。
7. 下一步计划：下一轮要做什么，以及为什么。
