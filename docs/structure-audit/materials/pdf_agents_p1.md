## 0. 一句话结论

**生产级 Agent ≠ 更强模型。**  
最小可跑：`Agent = LLM + 上下文 + 工具`。  
生产可靠：`Agent = Model + Harness`，Harness = 上下文 + 工具 + **约束 + 验证 + 纠正**。  
竞争力在模型之外；评估驱动迭代；实践在前、命名在后。

```text
                    ┌─────────────────────────────────────┐
                    │  Agent = Model + Harness            │
                    └─────────────────────────────────────┘
         Model(LLM)          Harness
         ─────────    ──────────────────────────────
         策略/大脑     Context  Tools  Constrain  Verify  Correct
                        眼睛     手脚    边界       对错     恢复
                              └──── 核心能力 ────┘└── 生产保障 ──┘

  Demo 视角:  LLM + 上下文 + 工具          → 能做事
  生产视角:  同上 + 约束 + 验证 + 纠正    → 可靠地做事
```

## 1. 核心公式与三层语言

### 1.1 实现 / 直觉 / 学术 三层同构

| 直觉 | 实现 | 学术（RL） | 职责 |
|------|------|------------|------|
| 大脑 | LLM | Policy | 理解、规划、决策「下一步做什么」 |
| 眼睛 | 上下文 | Observation Space | 决策点可见的全部信息 |
| 手脚 | 工具 | Action Space | 可执行动作集合（含 Skills、代码、子 Agent、事件、沟通） |

**不可缺一。** 未进入观察空间 ≈ 不存在；未进入动作空间 ≈ 只能写字不能改世界。

### 1.2 生产形态方程（书中展开式）

```text
Agent = LLM + 上下文 [+ 工具 + 约束 + 验证 + 纠正]
      = Model + Harness
```

| 层 | 一句话 | 与上下文/工具关系 |
|----|--------|-------------------|
| Context | 提供感知信息 | 核心能力 |
| Tools | 提供行动手段 | 核心能力 |
| Constrain | 能做/不能做什么 | 围绕上下文与工具的安全边界 |
| Verify | 自动判断结果对错 | 围绕工具结果的检查 |
| Correct | 失败时修正/回退/熔断 | 围绕调用失败的恢复 |

**产品成熟度不对称：** 早期框架重心在「能做事」（上下文+工具）；生产级重心在「不做错」（约束+验证+纠正）。Claude Code 类系统中，Harness 代码大半是后三者。

### 1.3 退款例子（有无 Harness 天壤之别）

| 缺项 | 无 Harness | 有 Harness |
|------|------------|------------|
| 上下文 | 看不到退款政策 | 系统提示写明 7 天政策 |
| 工具 | 不知调哪个 API | `query_order` / `process_refund` |
| 约束 | 无金额边界 | 退款额 ≤ 订单额 |
| 验证 | 编造「已退款」 | 校验 DB 状态 |
| 纠正 | 用户发现未退 | API 超时自动重试 |

## 2. 观察空间 × 动作空间：模型与世界的接口

### 2.1 接口优先于换模型

固定底层模型时，**重定义/扩展观察空间与动作空间** 往往是提升任务表现的主手段：把所需数据纳入上下文、把操作封装成工具，无需立刻再训模型。

### 2.2 产品演进 = 接口边界演进

| 产品 | 观察空间扩展 | 动作空间扩展 | 启示 |
|------|--------------|--------------|------|
| Manus | 网络/网页 + 屏幕 | 文件系统/代码 + 点击输入 | 合并 Deep Research / Coding / Computer Use 三路线 |
| OpenClaw | 多消息渠道 + 本地/云文件 | 本地优先 Gateway + 插件/Skills | 本地优先扩大数据边界 |
| Coding Agent | 代码库、终端、需求 | 搜索/读写/命令 | 增量：理解→搜索→改→测→修 |
| Deep Research | 网/学术库/本地 | 搜索、阅读、摘要 | 迭代深化 |
| Computer Use | 屏幕/浏览器 | 点击、输入、截图 | 感知→定位→操作→验证 |
| Pine 等办事 Agent | 账户/账单/知识库 | 电话、邮件、表单、用户确认 | 长程多步协商 |

### 2.3 扩展原则：按需、相关、可控

- **不要**一次性塞满信息与工具列表（噪声 + 选择成本 + 安全面）。
- **要**：检索把正确信息入上下文；工具发现只暴露当前动作；权限 + 结果验证约束动作。

### 2.4 共同特征（生产 Agent）

开放式动作空间、内部思考、持续交互（环境反馈调整策略）。

## 3. 上下文五组件与消融证据

### 3.1 每次 LLM 调用的上下文构成

| # | 组件 | 动静 | 作用 |
|---|------|------|------|
| 1 | 系统提示词 | 静态前缀 | 身份、权限、行为准则；可含用户记忆/环境状态 |
| 2 | 工具定义 | 静态前缀（可按需加载 schema） | 可识别/可调用的动作 |
| 3 | 用户消息 | 动态轨迹 | 请求；可含 RAG 注入知识 |
| 4 | 模型回复 | 动态轨迹 | reasoning / content / tool_calls |
| 5 | 工具结果 | 动态轨迹 | 下一步依据；闭环反馈 |

```text
上下文 = 静态前缀(系统提示 + 工具定义) + 轨迹(user / assistant / tool 历史)
```

API 角色：`system` / `user` / `assistant` / `tool` + 顶层 `tools` 字段 ≡ 上述五组件。  
**无状态 API：** 每轮必须完整重发 messages；模型只基于请求内信息决策。

### 3.2 消融结论（实验 1-1）

| 缺失 | 现象 | 生产含义 |
|------|------|----------|
| 工具定义 | 无法调用工具 | 无手脚 |
| 工具结果 | 盲目循环同一调用 | 无闭环 = 无限循环 |
| 思考过程 | 前后决策矛盾 | 轨迹可解释性与连贯性 |
| 历史消息 | 失忆、重复已完成步骤 | 任务连贯性 |

**原则：上下文决定「能看到什么」；Agent 只能基于所见决策。**

### 3.3 上下文是能力上限（第 2 章开篇）

- 模型智力是基础；**上下文质量才是真实上限**。中等模型 + 好上下文 > 顶级模型 + 信息饥荒。
- Coding Agent 最低三类信息：实时代码结构/规范、流程规范（Git/CI）、环境信息（部署/密钥管理方式）。
- 上下文工程既是技术问题，也是**组织/文档化**问题（隐性知识无法进 context 则 Agent 无能）。
- 翁家翌要点：人和模型最重要都是 Context；团队最大问题是 context 不一致。

## 4. ReAct 与轨迹

### 4.1 循环

```text
思考(Reason) → 行动(Act / tool_calls) → 观察(tool results) → …
直至退出条件
```

退出条件（任一）：任务完成 / 调用 final_answer / 无工具调用的最终回复 / 错误次数超限 / 最大轮次。

### 4.2 轨迹特性

- **累积性：** 每轮 LLM 见完整历史 → 知阶段、已试、结果。
- **结构化：** user / assistant(reasoning+tool_calls) / tool 可分 → 可解释、可调试。
- **学习资产：** 轨迹可入知识库、可 RL、可做行为模式分析。
- **成本注意：** 完整历史使成本随轨迹近似二次方增长（书中思考题；压缩在后文）。

### 4.3 工具调用四步（API）

1. 声明 tools（名/用途/参数）  
2. 模型决定是否调用、哪个、参数  
3. 框架执行，结果以 `tool` 消息追加  
4. 模型基于结果继续或最终回复  

无数据依赖的多 tool_calls 可**并行**；参数依赖前结果则串行下一轮。

### 4.4 模型即 Agent vs 框架职责

- RL 内化的是 **决策策略**（何时/调哪个/何参数），不是把搜索引擎/沙盒装进权重。
- 工具实现、沙盒、发起与回传仍在 **框架/服务端基础设施**。
- 编排循环可从客户端迁到服务端，但 **并未消失**。
- 模型越强，外围 Harness（约束/验证/纠正）越关键。

### 4.5 学习三路径（非互斥，不同时间尺度）

| 路径 | 载体 | 特性 |
|------|------|------|
| 任务内适应 | 当前上下文（示例、状态、检索） | 即时、低成本；任务后不自动持久 |
| 外部产物更新 | 知识文档 / Prompt·Skill / 程序·Harness | 跨任务、可审计；需检索或工具接入 |
| 参数更新 | SFT / 偏好 / RL | 高维能力与泛化；训练与回归成本高 |

协同：**临场适应 · 可控积累 · 能力内化**。

## 5. Harness 工程：生产竞争力

### 5.1 工程范式演进（层层包含，非替代）

```text
软件工程
  ⊂ 提示工程（优化输入指令）
    ⊂ 上下文工程（系统管理「模型能看到什么」）
      ⊂ Harness 工程（模型运行环境：约束/验证/反馈/恢复）
        ⊂ Loop 工程（跨轮持续自主：下一件事、验证、完成定义）
          〜 Graph 工程（执行图视角：节点/边/检查点状态；非 GraphRAG）
```

模型能力商品化后，差异迁到 **模型之外的工程**。例：LangChain Terminal Bench 靠改 Harness（自检结果、检测重复循环、优化思考策略）而非换模型提分。

### 5.2 五功能核心原则表

| 功能 | 核心原则 | 例子 |
|------|----------|------|
| 上下文 | **信息充分性**：决策点有足够信息 | 系统提示、知识库、状态栏、Sidecar 旁路查询 |
| 工具 | **接口清晰**：命名直观、参数有例、边界说明 | MCP、代码解释器、搜索 |
| 约束 | **故障安全默认**：能力默认关，必须显式开 | 每工具默认需用户授权（类 App 权限） |
| 验证 | **输入隔离**：安全检查看结构化数据，不信自由文本 | Linter、类型系统、工具结果 JSON 字段校验 |
| 纠正 | **确认不可恢复前不暴露中间态** | 静默重试、接续生成、连续失败熔断→人工 |

五者闭环：缺一即可靠性缺口。

### 5.3 Claude Code 类 Harness 机制清单（书中列举）

- 流程状态管理（执行到哪一步）  
- 多层上下文压缩  
- 权限分类（何操作需确认）  
- 熔断器（连续错误停重试）  
- 错误恢复（捕获、回滚稳定态、重试或交人）  

### 5.4 构建有效 Agent 的三条原则（Anthropic 经验）

1. **保持简单** — 最简方案起步；直接 API > 厚框架；清晰代码 > 聪明抽象；每层抽象 = 调试盲区。  
2. **保持透明** — 规划步骤、执行日志、决策轨迹可见；黑箱错误无法定位与纠正。  
3. **设计好 ACI（Agent-Computer Interface）** — 从 **Agent 视角** 设计接口，非程序员 API 视角；用设计防呆（Poka-yoke）：错误结构上不可发生（SIM 缺角、微波炉门未关不加热）。模糊接口会被模型放大为系统性错误。

### 5.5 工具设计原则（第 1 章工具节）

| 原则 | 内容 |
|------|------|
| 从窄到宽 | 任务最窄能力起步，再扩展 |
| 通用 vs 专用 | 通用基础能力（如沙盒 Python）用于组合探索；高风险/强规则操作用专用工具（参数明确、权限受限、可审计、预览/人确认） |
| 沙盒默认 | 隔离、默认可断网、限路径/时间/CPU/内存/输出 |
| 长程工作区 | 受控虚拟目录存计划/中间结果/日志/产物；防路径越界 |
| 五类工具 | 感知 / 执行 / 协作 / 事件触发 / 用户沟通 |
| 质量后果 | 接口不清→乱用；错误处理差→死锁；权限过宽→不可挽回 |

### 5.6 Harness 与「苦涩的教训」

立场：**方向认同，节奏务实。**  
模型会逐步「吃掉」Harness 层，但训练周期以月计，业务约束无法一次内化。  
**模型做不稳的，Harness 先补；模型内化一层，Harness 卸一层，去兜新前沿。**

## 6. 编排：工作流 vs 自主

### 6.1 从简单到复杂（默认顺序）

```text
单次 LLM（提示+上下文够用）
  → 工作流（固定可分解子任务）
    → 自主 Agent（动态路径、环境反馈）
```

Agent 用 **延迟与成本** 换性能；须显式权衡是否值得。

### 6.2 工作流

- 路径由代码写死；LLM 仅在节点内理解/生成。  
- **优势：** 严格流程控制（付款前不能订座）；攻击面限在单节点。  
- **局限：** 未覆盖分支只能异常处理或交人。

### 6.3 自主 Agent

- 路径实时决定 = ReAct 工具循环。  
- 须有 **停止条件**（完成 / 最大迭代 / 不可恢复错误），防死循环与过度执行。  
- 适用开放式问题（SWE-bench、Computer Use、迭代研究）。  
- 部署：沙盒充分测、护栏+监控、关键点人机检查点。

### 6.4 混合

合规/关键路径用工作流；灵活决策段用自主（如 n8n 同图混节点）。

### 6.5 框架选择标准

框架价值不再等于「编排 LLM」本身，而在 **最小抽象下的上下文管理、工具生态、安全约束、错误恢复**。选框架看能否让你专注业务逻辑，而非框架复杂度。

| 取向 | 代表（书中表） |
|------|----------------|
| 轻量自主 | OpenAI Agents SDK |
| 生产自主+子 Agent | Claude Agent SDK |
| 工作流+自主 | LangGraph、n8n、Dify |
| 角色多 Agent | CrewAI |
| 自托管全能 | OpenClaw（自主+事件驱动） |

## 7. 护栏与安全（架构问题，非上线补丁）

### 7.1 分层防御

单护栏不够；多专用护栏组合。先覆盖已识别风险，发现新洞再加。

**误拒绝也是失败：** 评估须测「应拒是否拦截」**与**「明确允许是否能完成」。合法敏感任务应提供解释、人工升级或授权路径，而非笼统拒绝。

### 7.2 三侧护栏

| 侧 | 机制 |
|----|------|
| 输入 | 相关性分类器；安全分类器（越狱 vs 提示注入：用户绕限 vs 外部数据间接操纵）；内容审核；规则（黑名单、长度、正则） |
| 执行 | 工具风险评级（可逆性/权限/财务影响 → 低中高）；高风险额外审查或人确认 |
| 输出 | PII 过滤；品牌/价值观一致性校验 |

### 7.3 人工干预触发

1. **超过失败阈值**（重试/操作次数上限）→ 升级人工  
2. **高风险操作**（敏感/不可逆/大额）→ 至少在信任建立前强制监督  

优雅移交：客服升人、Coding 交回开发者。

### 7.4 安全横切全书映射（书中表摘要）

| Harness 重点 | 章 | 安全关注 |
|--------------|----|----------|
| 上下文设计 | 2 | 提示注入、信息泄露 |
| 知识持久化 | 3 | 敏感暴露、隐私 |
| 工具设计 | 4 | 误操作、未授权、不可逆 |
| 验证与纠正（代码） | 5 | 身份冒用、责任归属 |
| 系统级验证 | 6 | 评估/可观测 |
| 参数纠正 | 7 | 目标偏离、对齐 |
| 持续进化 | 8 | 记忆污染、不安全自修、能力漂移 |
| 多模态 | 9 | 多模态过滤、实时权限 |
| 多 Agent | 10 | 信任越界、共享资源冲突 |

安全贯穿：**模型、上下文、工具、协作、社会** 五层。

### 7.5 长时任务 Harness 模式（Anthropic 实践）

- **初始化 Agent：** 设环境、分解任务列表  
- **执行 Agent：** 每会话增量推进，留下清晰交接产物  
解决：**上下文耗尽**、**过早声明完成**（proposer-reviewer 类方法在引言亦提及）。

## 8. 模型选型原则（生产）

| 原则 | 内容 |
|------|------|
| 不唯榜 | 在**自己的任务**上评估（第 6 章） |
| 思考模型默认 | 多步/工具决策必须带 reasoning；仅极简单步可例外 |
| 策略边界 | 能力 ≠ 产品允许；测「是否愿意执行、接口是否暴露、ToS 是否允许」 |
| 业务关键 | 准备人工接管或其他合规模型替代路径 |
| 延迟 | 输出 token 速度 × 多轮 = 端到端延迟 |
| 多模态 | 需要则硬性条件 |

## 9. 评估与迭代（引言硬原则）

- **没有评估，就没有进步。** 分辨改动是真进步还是运气。  
- 真实业务对能力上限的高压 + 评估机制 → 倒逼 Harness 原则（实践在前，命名在后）。  
- 不要等业界流行名词才动手。  
- 消融是默认方法：逐组件去掉，证据驱动而非理论推断。

## 10. 能力更新与持续进化（引言/第 1 章预告）

运行经验可沉淀为：知识文档、指令/Prompt/Skills、程序/Harness、模型参数；再经验证、灰度、回滚。  
**完成 ≠ 进步：** 可验证闭环需边界与安全（第 8 章展开，p1–40 仅建立框架）。

## 11. 与 structure-audit 清单的直接映射

| 书原则 | 建议 audit ID | 可观测判据（falsifier） |
|--------|---------------|-------------------------|
| Model+Harness 五件套 | H1 | 约束/验证/纠正可独立开关、可消融 |
| ReAct + 停止条件 | H2 | max_iter / 熔断 / final_answer 可触发 |
| 上下文 = 前缀+轨迹；充分且可管理 | H3 | 非全量倾倒；可压缩/按需 Skills |
| ACI 工具接口 | H4 | 结构化完整返回；高风险专用+审计 |
| 轨迹可解释可学习 | H5 | 可回放 run；user/assistant/tool 分栏 |
| 评估驱动 | H6 | 改 Harness 前后有可重复分 |
| 协作有真实 IO | H7 | 非人格 cosplay；有交接产物 |
| 经验→验证→发布→回滚 | H8 | learn 边存在，完成≠默认成功 |
| 工作流/自主按风险混用 | L\* 编排 | 合规步不可跳；开放步可 ReAct |
| 人在关键点 | 人机边界 | 高风险与超阈值必须升级，非常态签到 |

## 12. 第 1 章小结（书原文结构压缩）

1. Agent = 大脑 + 眼睛 + 手脚，三者缺一不可。  
2. **扩展眼睛与手脚**是模型固定时的主杠杆；扩展须按需+权限+验证。  
3. **上下文**由静态前缀 + 动态轨迹构成；消融证明组件不可替。  
4. **Harness** 是竞争力：生产代码大半在约束/验证/纠正。  
5. 编排顺序：提示 → 工作流 → 自主；无通用最优。  
6. **安全是架构问题**，从第一行代码考虑。

## 14. 可执行检查清单（生产 Agent 自检）

```text
[ ] 公式：是否有 Model 与 Harness 分层，而非「只调模型」

[ ] 轨迹是否可回放、可消融评测
[ ] 编排：固定合规步是否工作流硬编码；开放步是否自主
[ ] 评估：改 Harness 前后有无同集对比
[ ] 文档/知识是否足以填满「新员工」式 Agent 的最低 context
```
