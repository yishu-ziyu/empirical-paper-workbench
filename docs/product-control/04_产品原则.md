# 04 产品原则

## 原则 1：先让用户有把控感

用户进入产品后，必须知道：

- 我现在在哪一步。
- 系统正在做什么。
- 下一步该我做什么。
- 哪些内容已经有证据。
- 哪些内容还只是草稿。

如果页面很酷但用户不知道下一步做什么，就是失败。

## 原则 2：AI 给建议，人保留判断权

Agent 可以自动生成：

- 研究任务书。
- 变量候选。
- 方法候选。
- 执行计划。
- 草稿文本。
- 修订建议。

Agent 不可以静默覆盖：

- canonical VariableRoleSet。
- canonical DesignSpec。
- canonical RunPlan。
- 正式论文正文。
- 正式参考文献。
- 最终导出包。

正式层必须经过人工确认。

## 原则 3：证据比文本重要

这个产品的价值不在于写出漂亮段落，而在于知道每个段落能不能被证据支撑。

任何要进入论文的内容都必须回答：

- 证据在哪里？
- 是数据文件、执行结果、外部文献还是人工审阅？
- evidence_id 能否找到对应表格、代码、日志或引用？
- 结论是否和结果一致？

如果证据缺失，产品应该阻断，而不是润色。

## 原则 4：草稿层和正式层分开

论文应该像 Git 一样管理：

- 草稿层：可以快速生成、重写、试错。
- 审阅层：检查证据、方法、引用和一致性。
- 正式层：只有通过 gate 后才写回。

这样用户可以大胆使用 Auto Mode，同时不用担心正式稿被 AI 悄悄改坏。

## 原则 5：本地优先，但不放弃云端

第一版先把本地工作流跑通：

- 本地数据。
- 本地日志。
- 本地模型或 Codex provider。
- 本地 Git 状态。
- 本地复现包。

云端版后续复用同一套对象：

- ResearchIntent
- VariableRoleSet
- DesignSpec
- RunPlan
- EvidenceRegistry
- AgentTaskQueue
- ExportPreflight

不要把本地版和云端版设计成两个割裂产品。

## 原则 6：少展示，按需展开

默认界面只显示当前阶段需要决策的 3-5 个信号。

进入展开区的内容：

- 长日志。
- 工具调用。
- token 成本。
- 权限。
- 方法细节。
- evidence dump。
- Agent trace。

主屏服务决策，抽屉服务审计。

## 原则 7：每个开发节点都要有落点

每次开发必须回答：

- 改完后用户能多完成哪一步？
- 新增了什么可见反馈？
- 产生了什么真实文件或状态？
- 用什么方式验收？
- 是否更接近作品集 MVP？

不能只做“看起来推进了”的循环任务。
