# 当前前端交互基线（2026-09-17）

> 业务顺序更新：用户已确认“明确研究意图 → 数据可行性检查 → 确认可执行设计 → 正式分析”，详见 [研究意图到可执行设计](research-intent-to-design.md)。下文的“分析进行中”不得被解释为数据检查前已经获准正式估计；技术确认链接线与体验设计分别验收。此前提出的首轮固定展示“问题/比较/结论边界”未被采纳，不作为本文件要求。

> 这是当前讨论与后续 Coding Agent 交接的**唯一设计基线**。聊天截图、临时 HTML、旧探索稿只作参考；发生冲突时，以本文件 + 当前分支代码/运行事实为准。

## 0. 工作规则

**总是以事实为准，不要附和我。** 若用户口述与代码、运行结果、测试或截图冲突，以可验证事实为准，并明确指出冲突。

- GitHub commit 是双方同步点。任何“已确认方案”必须落到仓库文件并有 commit。
- 不得把设计审阅稿说成已接入业务；不得伪造后端状态、统计结果或能力。
- 未经本地运行/测试，不得声称“已工作”或“已通过”。

## 1. 本轮融合目标

用户明确给出两类偏好：

1. **保留远端已有 `docs/design/first-value-entry/` 的视觉底色**：纸张感、暖灰/米白背景、墨色文字、低饱和绿色、Serif + Sans + Mono 的编辑型气质，以及克制的分隔线和留白。
2. **不采用该旧稿的排版布局**。当前接受的布局方向来自本轮“渐进式研究流”原型：页面稀疏、一个屏幕只处理一个焦点、研究系统随着人的思考逐步显形。

当前不是最终视觉定稿；用户只确认“这个方向可以继续抠细节”。

## 2. 信息披露顺序

默认体验按下面顺序长出来，而不是一开始展示完整工作台：

1. **一个想法**：首屏只问“你想说什么”，允许顺手写预期。
2. **一个追问**：Agent 一次只问一个真正影响研究方向的问题。
3. **确认研究问题**：把用户原话整理成可编辑的研究问题/预期，用户确认。
4. **数据进入**：这时才要求挂数据/选择案例；先检查“手上有什么”，不自动把全部分析结果铺出来。
5. **分析进行中**：默认只显示一句当前状态；“正在做什么/路径”属于次级信息，用户主动展开才看。
6. **候选设计**：Agent 说明“为什么值得试”，但不把候选路线说成已采用主规格。
7. **方法预检**：正常时安静通过；只有发现需要人判断的问题才中断并交证据。
8. **第一条真实证据**：先给最小结论，再允许下钻到另一条估计、设定、来源、trace/code。
9. **工作台后置**：当研究对象已经积累到需要跨区域回看时，才展开工作台导航/账本；不是首屏。

## 3. 分析阶段的动效与披露

目标不是“看起来在忙”，而是让用户理解 Agent 的推进，并避免伪造进度。

### 默认可见

- 一句当前动作，例如“正在确认变量是否能回答这个问题”。
- 一个安静呼吸的状态点。
- 可停止/暂停时，提供真实可用的停止/暂停动作。

### 用户展开“这一步怎样推进”后

按真实事件逐项出现：

- 已完成：实心点 + 文案稳定留存。
- 当前：空心绿点/轻呼吸。
- 未开始：低对比度，不做假进度条。

如果后端没有阶段事件，就不要编造百分比、倒计时或假步骤。

### 结果出现

- 新信息采用现有 `slideUp` / `wb-pane-in` 一类 150–250ms 的轻微进入。
- 数字不做老虎机式 count-up，不用动画制造“计算精度感”。
- 如果需要比较两条结果，优先先出现主结果，再通过“还有一条估计给了不同答案”主动披露第二条，而不是首次就并排塞满。
- 来源/公式/trace/code 均按需下钻，不常驻首屏。
- 导出代码对话框的第一项是“复现包 · 实际运行的代码”（附“只下载脚本”）；原有 Python / Stata / R / EViews 四种放在“翻译版 · 数值未核对”下。复现包下载失败时说明原因（没有设定运行 / 数据已变），不静默。

### Agent 光标

可复用现有 `AgentCursorLayer` 的语义：只在“它正在检查某个明确对象”时短暂出现，指向真实目标；不要作为常驻装饰。

## 4. 账本与对话

- 对话 = 用户控制研究的主入口。
- 账本 = 机器做过什么、用户决定过什么的审计历史。
- 账本默认只读，不成为第二套表单/第二个真相来源。
- 可在账本提供“重新运行 / 从这里分叉 / 采用这个结果”这种显式动作；动作产生新状态，不直接篡改历史事实。
- 失败尝试完整留账本；论文只消费用户明确采用的结果。

## 6. 本轮审阅稿

当前融合审阅稿：

`docs/design/progressive-research-flow/index.html`

它只验证“视觉底色 + 渐进披露 + 分析阶段动效/披露”的交互方向，不代表正式业务已经接线。

审阅时重点看：

1. 首屏是否足够空，只聚焦“你想说什么”。
2. 每一步是否真的只新增当前需要的信息。
3. 分析等待时是否有可理解但不伪造的反馈。
4. 第一条结果是否足够克制，第二条结果是否在主动动作后再披露。
5. 整体是否继承旧稿的纸张/编辑气质，而不是回到 SaaS 仪表盘。

## 7. Agent ↔ Agent 交接协议

任何 Agent 做完工作后，必须留下下面的事实。PR 场景以 `.github/pull_request_template.md`
为唯一人工填写入口；CI 自动生成 `base_sha` / `head_sha` / merge-base / changed files 与检查结果，
不要再手抄这些容易漂移的机器事实。非 PR 交接仍可使用完整文本块：

```text
HANDOFF TO NEXT AGENT
repo: yishu-ziyu/empirical-paper-workbench
branch: <branch>
base_sha: <sha>
head_sha: <sha>

changed_files:
- ...

what_changed:
- ...

runtime_evidence:
- 实际打开/运行了什么：
- 实际观察到什么：

verification:
- command: ...
  result: PASS/FAIL + 关键原始结果

known_gaps_or_disagreements:
- ...

facts_vs_requests:
- 用户口述与代码/运行事实冲突处；没有写 none

commits_pushed:
- <sha> <message>
```

接手 Agent 必须先读本文件，再看目标分支相对 `main` 的 diff，不得只依据上一位 Agent 的自然语言总结。

PR CI 至少校验：

- `base_sha + head_sha` 的真实 merge tree 可以生成；
- 三点 diff 无 whitespace error；
- `what_changed`、`runtime_evidence`、`known_gaps_or_disagreements`、
  `facts_vs_requests` 四段人工事实非空。

机器能够从 Git 得到的内容不要求人重复维护；机器无法知道的运行证据与分歧必须由人明确写出。
