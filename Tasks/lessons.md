# Lessons

## 2026-05-28：P 阶段组件完成后必须汇报功能效果和对接方式

用户反馈：每次做完一个组件后，不能只汇报改了什么、测了什么；需要同步这个组件达到什么效果、具备什么功能、下游如何对接。

后续规则：

- 每个 P 阶段节点完成后，收尾必须先说明“组件效果”：它现在让系统多了什么可用能力。
- 必须说明“对接方式”：上游输入是什么、输出文件/状态是什么、下游下一步读取哪个字段或文件。
- 必须说明“当前不能做什么”：尤其是是否仍停在草稿层、审批层、预检层，是否没有写正式层。
- 技术文件、测试命令和 schema 作为证据放在后面，不能替代产品/组件效果说明。
- `Tasks/todo.md` 的节点记录也要包含效果和下一跳，不只记录测试通过。
- 面向用户同步时少用实现细节和内部技术名词；除非用户追问，默认用短句说明产品效果、可验收入口、当前边界。

## 2026-05-25：Task Brief 页必须引导决策，而不是展示组件结构

用户反馈：提交题目后进入任务处理页，用户仍不知道自己到底在干嘛。问题不是单纯“不够好看”，而是页面没有引导用户完成当前决策。

后续规则：

- Task Brief 页不是 dashboard，也不是组件说明页；它必须先回答“现在要确认什么、为什么确认、确认后会发生什么”。
- 主屏只展示一个主决策和一个主动作；证据、风险、派工、正式层边界进入右侧 Inspector 或按需展开。
- 不在主屏使用 `Inspector`、`Task Brief`、`SupervisorPlan`、`草案层判断`、`候选，不写回` 这类内部实现词作为理解页面的前置条件。
- 用户无需理解产品状态机，也应该能在 5 秒内知道下一步该点哪个按钮。
- 下游阶段在当前 gate 未完成前可以展示路径，但必须显式标记待解锁，不能让用户误以为已经进入分析阶段。

## 2026-05-25：不要把本地版和云端版设计成两套割裂产品

用户反馈：双模式会把产品搞复杂。应该先把本地高效工作流做好；云端版本复用同一套产品路径和状态机，只替换执行环境、数据入口、权限和资源控制。

后续规则：

- 不再说“本地模式一套、云端模式一套”。
- 默认是一套产品流程：题目输入 -> 任务书 -> SupervisorPlan -> Agent Task Queue -> Auto Mode 到下一个人工 gate。
- 本地优先只是实现顺序，不是另一套用户体验。
- 云端上线时复用同一状态机；差异限制在文件上传、模型 provider、权限、成本和隔离策略。
- 文档中避免把同一交互决策拆成 local/cloud 两个相互矛盾的行为。

## 2026-05-25：Codex 不再负责高保真视觉设计，只交付交互契约和功能接入

用户反馈：当前 React Demo 视觉质量不达标；后续高保真界面由 Kimi / 其他前端设计模型完成。Codex 不应继续直接做视觉设计，而应提供技术文档、设计方案、状态契约、接口契约、测试和功能接入。

后续规则：

- Codex 负责：信息架构、交互决策树、状态机、API contract、数据字段、验收标准、测试、后端和前端数据接入。
- Kimi / 前端设计模型负责：高保真视觉、版式、动效、具体组件外观、审美调性。
- Codex 可以做低保真 Demo 验证流程，但必须明确“非视觉稿”，不能把低保真样式当最终方案推进。
- 当用户要求“讨论每个板块 UI”时，Codex 输出应是可交给前端设计器的 UI contract，而不是直接写 CSS 追求美观。
- 已确认交互决策必须写进 `docs/architecture-v2/` 或 `Tasks/decision-log.md`，避免下一轮重复讨论。

## 2026-05-25：新工作台模块必须先有设计契约，再接业务工作流

用户反馈：其他模块的设计要先规范好，规范好之后才能接具体工作；否则旧前端的信息拥挤、解释性文案和功能堆叠会在 React 新入口里复发。

后续规则：

- 每个 React 工作台模块先定义主决策、默认摘要、右侧 Drawer 详情、空态、加载态、错误态和正式层写回边界，再接真实 API。
- 主屏不显示“为了防止风险...”这类解释性防守文案；风险和证据要求放进用户点击后的审阅层。
- 任何高噪声信息，包括日志、JSON、权限、成本、证据明细、Agent 工具调用，都默认进入右侧 Drawer 或折叠详情。
- 设计契约必须能被测试锁住；不能只靠口头审美判断。

## 2026-05-25：本地 Auto Mode 不能 fallback-first，必须 best-available-first

用户反馈：既然目标是最好的本地科研 OS，就不能默认做一个保守 dry-run 或半吊子候选层，然后停下来解释风险。

后续规则：

- 本地 CLI / Auto Mode 默认追求当前机器可用的最高能力：StatsPAI、StataMCP、CNKI、Web、Zotero、本地数据、LLM Supervisor、agentmemory 都应被探测或接入。
- 不可用能力必须写入审计状态，说明缺什么、为什么不可用、下一步怎么接入；不能静默跳过。
- 自动产物可以大胆生成草案层，但所有会影响正式研究结论的写回必须经过人工 review。
- 完成后必须同时报告：已经真实跑通的能力、只是探测到但尚未接入的能力、因为安全边界刻意不做的写回。
- 如果全量测试不绿，必须明确说出失败测试属于当前改动、既有漂移还是下一轮前置修复，不能只报目标测试通过。

## 2026-05-25：用户给出明确 UI 原型时，先做原型本身，不要泛化成全局设计

用户反馈：后面不同板块会有不同 UI 偏好，当前发来的 Claude-style 输入器和滑动标签就是先要做的事情；并且第一版基本只想要黑白灰。

后续规则：

- 当用户给出明确 UI 组件代码或截图，并说“这就是我喜欢的设计”，先实现该组件切片，不要先扩展到全局 IA、完整模块重排或其他风格探索。
- 新前端第一阶段不要把所有产品能力铺满；输入器、附件、模式选择和阶段导航应保持强留白和低信息密度。
- 对该用户当前产品，黑白灰是默认安全配色；除非用户另行指定，不用彩色状态色表达 UI 层级。
- 旧前端只有在新 React 入口被用户认可后再删除，避免同时丢失可用回退面。
- 首屏不要放“我们现在只验证…”、“不展开…”、“不会静默…”这类防守性说明；这些边界应放到具体审阅、提交、写回动作的确认层里。
- 黑白灰不等于纯黑纯白；用户当前偏好是低对比、干净、未来感，强对比需要主动下调。

## 2026-05-13：任务收尾说明必须产品化

用户反馈：每次完成任务后，如果只解释代码、测试和内部状态，会跟不上当前产品开发进度。

后续规则：

- 每次完成一轮开发，先用产品语言说明“这轮对用户体验/产品流程改变了什么”。
- 必须明确页面入口：用户打开哪个 URL、点击哪个导航、看哪个面板、哪个按钮能验证。
- 剩余风险要写成产品风险，而不只是工程风险。例如“还不能写回正文”“还没有 docx 导出预检”“本地验收产物未决定是否进入 fixture”。
- 下一步计划要说明为什么是下一步，以及它在研究生命周期中的位置。
- 技术细节、测试命令和文件路径放在后面，作为证据，不作为唯一汇报主体。

推荐收尾结构：

1. 产品进展：这轮让用户现在可以做什么。
2. 你可以怎么验收：页面入口、点击路径、应看到的状态。
3. 行为覆盖：对应 BDD 行为。
4. 测试覆盖：命令和结果。
5. 实现范围：关键文件和接口。
6. 剩余风险：产品风险优先，工程风险其次。
7. 下一步计划：下一轮要做什么，以及为什么。

## 2026-05-25：入口页只负责收集意图，分析组件必须后置

用户反馈：进入之后应该只有一个干净对话框；输入题目后才进入各个分析环节，分析环节里再出现卡片。

后续规则：

- Topic-first 首页不能放语义卡、审计日志、Agent 队列、阶段详情或技术解释。
- 任何“分析卡片”“证据卡片”“语义拆解”都必须进入提交后的工作区或阶段页。
- 首屏目标只有一个：让用户写下题目、附材料、选择模式并提交。
- 如果某个组件很酷但会增加首屏认知负担，默认后置到分析页。

## 2026-05-26：论文系统沟通不要防御式自我贬低

用户反馈：研究产出本来就是两阶段或多阶段过程，先写草稿，再补证据、审稿、润色和终稿；不要反复用“只能说明、不能说明、不要宣称”等防御式表达来描述阶段性成果。

后续规则：

- 把当前产物描述为“处在什么阶段、下一步补什么能力”，不要用自我贬低语气评价成果。
- 讨论论文质量时，直接给出可执行标准：结构、字数、文献闭环、方法诊断、审稿迭代、复现包，而不是停留在免责声明。
- 当发现差距时，把差距转成任务线并推进，例如“长篇正文生成器”“CNKI/Zotero 文献闭环”“Journal Skill 方法门”“审稿式修订循环”。
- 对外部竞品如 CoPaper 的差距分析要落到功能模块、数据流和验收命令，不用泛泛说“还不能达到”。
- 最终汇报要说“下一轮怎么把草稿推进到更高水平”，而不是反复强调当前不是终稿。

## 2026-05-26：P 阶段小节点必须 20 分钟时间盒

用户反馈：P4-A、P4-B、P4-C 这类小节点最多只能用 20 分钟；超过 20 分钟，要么说明节点太大，需要拆解，要么说明路线走错，需要换策略。

后续规则：

- 每个 P 阶段字母节点启动时先写一句验收目标和预计产物，不展开成大而散的任务。
- 单个小节点以 20 分钟为上限；接近上限时必须停下来判断：拆更小、换实现路线，或明确阻塞原因。
- Agent Team 必须用于提速和复核：启动前说明调用哪些 Agent，完成后说明什么时候收回、主 Agent 如何合并。
- 如果一个节点需要超过 20 分钟，必须升级为多个子节点，例如 `P4-H1`、`P4-H2`，每个子节点都有独立验收命令和产物。
- 质量不能用拖延换取；高质量的标准是小步闭环、真实验证、及时提交，而不是长时间不汇报。
- 这条规则适用于后续 P4/P5/P6 全部字母节点；不因为目标更大就延长单节点时间，而是通过拆分、并行 Agent Team 和更明确的验收标准保持速度。

## 2026-05-27：20 分钟节点规则升级为硬约束

用户反馈：每一个小节点，例如 P4-A/B/C/D 或 P6-G6x，最多只能用 20 分钟。超过 20 分钟，优先判断节点拆得不够小，或当前路线走错；不能用“还在做”来消耗长时间。

后续规则：

- 每个小节点启动前必须写清楚：本节点只解决什么、产物是什么、验收命令是什么。
- 每个小节点结束时必须写清楚：是否在 20 分钟内闭环、是否需要拆下一节点、是否有路线错误信号。
- Agent Team 默认用于提速和复核；如果线程上限或工具限制导致无法派出，必须记录失败原因，并继续走本地可验证闭环，不能停在调度失败。
- 小节点不得混合多个目标；例如“渲染 PDF”和“批准正式写回”必须拆成两个节点。
- 质量要求不降低：20 分钟限制约束的是任务切片大小，不是允许跳过 BDD/TDD、真实运行、测试、提交或人工 gate。

## 2026-06-10：Trace Learning 进入开发闭环

用户提供 Trace Learning 方法论：Agent 系统不能只靠“反思”变好；每个真实 bad case 都要绑定执行轨迹、用户反馈、错误分类、根因、修复层和回归验证。

后续规则：

- 用户在浏览器验收中指出错误时，先把它当作 bad case，而不是普通 UI 意见；记录输入、当前页面状态、错误表现、用户预期和相关文件路径。
- 每个高价值 bad case 必须归因到一层：prompt、skill/playbook、decision rule、knowledge base、retrieval、tool interface、memory、output format、clarification flow、product boundary 或 eval set。
- 修复不能只改 prompt；要说明实际修的是哪一层，并把同类问题转成 BDD/TDD、fixture、UI 契约或 CLI 回归测试。
- 如果用户反馈来自真实页面截图或浏览器评论，优先生成可回放测试或可验收步骤，避免只写解释。
- 每轮完成后，在汇报里说明“这次 bad case 被沉淀成了什么”：规则、测试、组件、服务恢复、skill registry、方法库补丁或产品边界。
