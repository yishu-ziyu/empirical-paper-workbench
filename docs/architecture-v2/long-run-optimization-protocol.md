# Long-run Optimization Protocol

本协议把长时间研究开发中的“平台期识别 -> 策略跃迁 -> 约束修复 -> 证据验收”固化为项目流程。它不替代本项目的 BDD + TDD 约定，而是在超过两轮迭代、预计超过一小时、或已经出现重复试错时，作为外层控制协议使用。

## 适用范围

- 研究问题、数据、变量角色、识别策略、执行后端、论文生成、产品功能等任一链路，连续迭代超过两轮。
- 同一类失败、同一类指标停滞、同一类日志异常反复出现。
- 需要让下一位执行者或下一次会话接上当前状态，而不是重新摸索。

## 核心定义

- 微调：在当前策略内做小幅参数、提示词、字段、阈值或实现修补。
- 平台期：连续尝试后没有产生可解释的指标改善、证据产物或瓶颈认知变化。
- 策略跃迁：主动切换到结构不同的方案，例如从提示词修补转向执行后端、从单方法验证转向多方法对照、从页面修补转向状态模型治理。
- 打破-修复：允许新方向短暂破坏非核心约束，但必须记录被打破的约束、修复计划、回滚点和验收证据。

## 每轮必须记录

每一轮长程研发必须更新 `Tasks/round-log.md`，至少包含以下字段：

```yaml
round_id:
objective:
current_best_result:
current_strategy:
changed_files_or_artifacts:
metric_delta:
plateau_check:
bottleneck:
next_strategy:
invariant_constraints:
rollback_point:
evidence_paths:
```

## 平台期触发条件

命中任一条件时，停止继续同策略微调，先做瓶颈诊断：

- 连续三轮同类尝试没有产生实质收益。
- 关键指标低于预设改变量，且无法解释差异来源。
- 同一错误、同一日志异常、同一验收失败重复出现。
- 本轮没有新增可核查证据产物。
- 执行者说不清当前瓶颈到底在数据、方法、执行、产品状态还是文稿表达。

## 策略跃迁菜单

出现平台期后，从下列方向选择一个结构性不同的下一步，而不是继续原地修补：

- 研究问题跃迁：重写问题边界、理论机制、可证伪命题。
- 文献证据跃迁：回到来源，补足变量、识别或机制证据。
- 数据跃迁：检查样本、缺失、合并、字段口径、版本冻结。
- 变量角色跃迁：重审因变量、核心解释变量、控制变量、工具变量、调节/中介变量。
- 方法跃迁：从 OLS 转向 IV/DID/RDD/PSM/DML，或从单方法转向稳健性矩阵。
- 执行跃迁：从文档/计划转向真实后端、真实 CSV、真实结果文件。
- 产品状态跃迁：从页面交互修补转向状态机、队列、权限、审计日志。
- 写作跃迁：从结果堆砌转向论证结构、表格证据、审稿人问题。
- 验证跃迁：从人工观察转向自动化测试、日志断言、结果文件比对。

## 不变量

策略跃迁可以打破临时实现约束，但不能打破以下不变量：

- 原始数据不可被静默覆盖。
- 已确认的变量含义、识别边界和证据边界不能被改写成更强结论。
- 不能把骨架文件、设计文档或 UI 状态当作真实执行证明。
- 真实执行证明必须能追到具体命令、日志、结果文件或测试输出。
- 每次跃迁必须有回滚点，并说明哪些改动是文档、哪些是代码、哪些是数据。

## 完成标准

长程任务只有在以下条件同时满足时，才可以标记为完成：

- `Tasks/round-log.md` 记录了最后一轮的目标、瓶颈、策略和证据。
- 相关 `Tasks/todo.md` 条目已勾选或明确留下未完成项。
- 证据路径存在，并且能证明真实执行链路或文档流程已经落地。
- 如果是代码或产品行为改动，测试、日志或浏览器验收已经完成。
