# Product Control Demo Line

## 目的

这条 Demo 线把产品控制台落到一个固定题目上。

它不是再开一个抽象规划文档，而是定义一个可以被用户验收、可以被面试官理解、可以被后续开发任务持续推进的最小作品集主线。

## 固定题目

题目：

> 父母受教育水平对子女工资收入的影响

选择这个题目的原因：

- 项目中已经存在 `Tasks/parent-education-wage/` 和 `Tasks/parent-education-wage-01-design-bdd.md`。
- 当前 URL 和运行痕迹已经多次使用 `parent_education_wage`。
- 这个题目能覆盖实证 OS 的关键链路：题目绑定、数据发现、变量角色、方法设计、结果证据、草稿边界。
- 它适合做作品集，因为问题直观、变量语义清楚、用户容易理解。

## 用户验收故事

### 1. 输入题目

Given 用户输入“父母受教育水平对子女工资收入的影响”

When 系统生成当前研究会话

Then 页面和 CLI 都只能显示这个题目的研究状态，不允许出现工业机器人、耐心资本、CGSS 幸福感等旧题污染。

业务意义：

用户先获得“这是我的题目”的把控感。

### 2. 确认任务书

Given 系统已经生成研究简报

When 用户打开任务书

Then 用户应看到研究问题、研究边界、数据线索、方法倾向、成功标准和下一步动作。

业务意义：

在进入数据和模型前，先确认研究方向没有跑偏。

### 3. 查看 Agent Queue

Given 任务书已确认

When 系统生成 Agent Task Queue

Then 用户应看到每个 Agent 要做什么、需要什么输入、产出什么文件、是否需要人工确认。

业务意义：

用户能理解系统正在如何推进，而不是只看到一段神秘的 AI 输出。

### 4. 数据与变量候选

Given 系统开始寻找数据与变量

When DataAgent 输出候选

Then 每个候选必须显示来源、路径、字段画像、证据等级和为什么适合当前题目。

业务意义：

变量推荐不能只靠“看起来合理”，必须能被审阅。

### 5. 方法设计

Given 变量候选已生成

When MethodAgent 生成方法建议

Then 系统必须说明推荐 OLS、FE、IV、DID 或其他方法的理由、前置条件、缺失证据和阻塞原因。

业务意义：

方法选择要像专家建议，而不是模板填空。

### 6. 执行与证据

Given 方法和变量已达到可执行状态

When 系统运行或预检执行任务

Then 结果必须绑定 run id、数据、脚本、参数、输出表格和 evidence_id。

业务意义：

论文里的每个数字都能追到来源。

### 7. 草稿边界

Given 系统生成研究报告或论文草稿

When 草稿引用某个结论

Then 该结论必须有 evidence_id；没有真实证据的内容只能进入“待补证据”或“研究计划”部分。

业务意义：

Auto Mode 可以写草稿层，但不能静默覆盖正式层。

### 8. 证据审计

Given 系统已经生成草稿或研究包

When 用户进入 Review / Evidence Audit

Then 系统必须列出：

- 哪些结论有真实数据支持。
- 哪些结论有真实运行结果支持。
- 哪些结论只是 LLM 推断。
- 哪些地方存在占位符、前后数字冲突或引用未验证。
- 当前是否可以导出，若不能导出，缺什么。

业务意义：

这个产品的核心不是“写得像论文”，而是让用户知道哪些内容可信、哪些内容还需要继续做。

## P0 开发拆分

### P0-A 题目绑定核验

目标：

让固定题目进入系统后，所有任务状态和展示都绑定当前题目。

验收：

- `Tasks/parent-education-wage/brief.md` 存在并只描述当前题目。
- 页面顶部、任务书、Agent Queue、Review 输出不出现旧题。
- 若检测到旧题内容，进入 evidence audit 的 critical issue。

### P0-B Agent Queue 显示

目标：

把 Demo 线拆成用户能理解的任务队列。

任务：

1. ResearchBriefAgent：确认研究题目和边界。
2. DataAgent：发现数据源和字段画像。
3. VariableAgent：生成变量角色候选。
4. MethodAgent：生成方法设计和前置条件。
5. ExecutionAgent：执行预检或真实回归。
6. EvidenceAuditAgent：审计证据链和草稿边界。

验收：

- 每个任务有负责人、输入、输出、状态、阻塞原因和产物路径。
- 默认展示摘要，详情按需展开。

### P0-C Evidence Audit

目标：

把“不能糊弄”的要求做成机器可读审计。

验收：

- 输出 `Results/json/product_control_demo_evidence_audit.json`。
- 输出 `Reviews/product_control_demo_evidence_audit.md`。
- 至少检查：旧题污染、占位符、evidence_id 缺失、结果文件缺失、样本量/系数冲突、未验证引用。

### P0-D 作品集验收包

目标：

把这个 Demo 变成可展示的作品集材料。

验收：

- `docs/product-control/07_作品集Demo脚本.md`
- 一张流程图。
- 一张 Agent 分工图。
- 一张证据审计截图或文字审计报告。
- 一份“当前做到哪里 / 还差哪里”的产品说明。

## 成功标准

这条 Demo 线跑通后，用户应该能用 3 分钟解释：

- 我在做什么产品。
- 用户为什么需要它。
- 它和普通论文生成器有什么区别。
- 当前系统能做到哪一步。
- 哪些地方还有风险。
- 下一步为什么值得继续做。

## 当前边界

- 不承诺直接生成投稿级终稿。
- 不把草稿层静默写入正式层。
- 不允许旧题污染新题。
- 不允许没有 evidence_id 的主结果结论进入正式输出。
- 不允许把 LLM 推断伪装成真实统计结果。
