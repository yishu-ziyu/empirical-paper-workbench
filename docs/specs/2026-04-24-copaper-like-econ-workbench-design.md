# CoPaper-Like Econ Workbench Design

## 1. 项目定位

这个项目不是做一个“论文文件夹模板”，而是要做一个面向经济学实证研究的本地优先研究工作台。终局目标是达到产品级能力：

- 从研究问题出发，指导完整的实证因果分析主链路。
- 把 `Data / Program / Results / Manuscripts / Git` 变成真正可执行的研究操作系统。
- 把 `Awesome-Agent-Skills-for-Empirical-Research` 作为研究工作流和方法论路由层。
- 把 `StatsPAI` 作为计量执行引擎。
- 最终可以演进为接近 CoPaper 的“一键生成论文初稿”的产品体验。

## 2. 用户与场景

### 核心用户

- 当前第一用户就是你自己。
- 用户画像：经济学本科生，目标是写出接近研究生水平的毕业论文。
- 这意味着系统必须同时满足两类要求：
  - 产品层面要有足够强的“指导性”，能补足经验差距。
  - 学术层面要有足够强的“透明性”，不能黑箱给答案。

### 核心场景

- 给定研究问题、候选数据和目标方法，系统指导完成一篇实证论文。
- 典型主链路：
  - 研究问题定义
  - 数据准备与清洗
  - 因果识别策略选择
  - 基准回归与稳健性分析
  - 结果组织
  - 论文草稿生成
  - 复现与版本管理

## 3. 终局能力定义

### A 阶段：个人本地研究助手

- 面向单用户。
- 本地优先。
- 命令行或脚本入口。
- 能跑通从数据到结果到论文草稿骨架的闭环。

### B 阶段：可演示原型

- 形成清晰的产品入口。
- 有任务状态、阶段面板、失败恢复。
- 可以向别人展示工作链路。

### C 阶段：产品雏形

- 以网页化产品形态存在。
- 用户通过自然语言和结构化表单同时驱动系统。
- 支持多个研究项目并行。
- 系统内置论文项目结构、分析流水线、写作装配、日志与可复现约束。

## 4. 设计原则

### 4.1 以 C 为终局倒推，不做无法演进的局部最优

- A 阶段不是临时脚本堆。
- B 阶段不是演示用假壳。
- C 阶段的关键能力边界，从 A 阶段就要确定。

### 4.2 本地优先

- 原始数据、脚本、结果、手稿都在本地项目目录内可追踪。
- 外部官网、第三方模型、在线服务是增强项，不是唯一依赖。

### 4.3 结构化优先

- 任何自然语言目标，最终都要落到结构化项目状态上。
- 系统不能只会“聊天”，必须会维护项目状态、阶段、产物和依赖关系。

### 4.4 可解释优先

- 每个分析结论必须能追溯到数据、脚本、结果文件。
- 每个推荐方法必须能说明“为什么是这个方法，而不是另一个”。

### 4.5 人机协作，不做不可控黑箱

- 系统应该极大减少你的研究成本。
- 但不能让你失去对论文逻辑、识别策略、稳健性和写作的控制权。

## 5. 系统分层

系统分成四层。

### 5.1 项目结构层

职责：

- 管理 `Data / Program / Results / Manuscripts / Submissions / Tasks / docs`
- 管理 Git 与 `.gitignore`
- 管理项目元数据和阶段状态

这是研究操作系统层。

### 5.2 工作流路由层

职责：

- 判断当前研究处于哪个阶段
- 决定下一步应该调用哪类能力
- 把任务路由到文献综述、识别策略、清洗、基准估计、稳健性、写作、降 AIGC 等模块

这层主要吸收 `Awesome-Agent-Skills-for-Empirical-Research` 的思想。

### 5.3 计量执行层

职责：

- 执行描述统计、回归、因果估计、稳健性检验
- 生成结构化结果对象
- 输出表格、图形、日志、模型说明

这层主要依赖 `StatsPAI`，必要时兼容 Stata / Python 混合执行。

### 5.4 论文装配层

职责：

- 把结果自动映射成论文段落骨架
- 维护摘要、研究设计、结果解释、稳健性章节
- 生成 Markdown / LaTeX 中间稿，再稳定导出到 `docx`

## 6. 为什么这套架构可以逼近 CoPaper

CoPaper 的本质不是“一个网站”，而是四件事的组合：

- 有研究方法论路由
- 有计量执行引擎
- 有论文装配器
- 有产品级入口和状态管理

你现在已经有了项目结构底座。只要把后三层补齐，就具备了走向 CoPaper-like 能力的可能。

## 7. 关键对象模型

系统内部至少需要以下核心对象。

### 7.1 ProjectState

记录整个论文项目的状态：

- 题目
- 研究问题
- 当前阶段
- 数据资产
- 方法选择
- 已生成结果
- 当前手稿状态
- 待办与阻塞

### 7.2 ResearchPlan

记录研究路径：

- 核心因果问题
- 主要识别策略
- 备选策略
- 关键变量
- 样本定义
- 核心稳健性方案

### 7.3 AnalysisRun

记录一次计量执行：

- 输入数据版本
- 使用方法
- 参数配置
- 输出表图
- 输出日志
- 诊断信息

### 7.4 ManuscriptDraft

记录论文稿件状态：

- 各章节内容
- 数据与结果引用位置
- 版本号
- 导出格式

## 8. 第一阶段的 MVP 不是降级，而是终局的最小闭环

第一阶段必须闭环完成以下内容：

- 用户定义研究问题
- 系统记录项目状态
- 用户指定数据源和变量角色
- 系统执行一次基准分析
- 系统执行一次稳健性分析
- 系统输出结构化结果到 `Results/`
- 系统生成论文草稿骨架到 `Manuscripts/`

如果这条链路跑通，就不是工具集合，而是真正的研究工作台雏形。

## 9. 第一阶段不做什么

为了保证终局清晰，第一阶段明确不做：

- 多用户协作
- 云端账号体系
- 在线数据库平台整合的大而全版本
- 花哨但不提升研究产出的前端视觉层

## 10. 成功标准

如果系统达到下面标准，就说明方向正确：

- 你可以用它推进自己的毕业论文，而不是只做演示。
- 它能显著降低你在识别策略、分析组织和写作衔接上的认知负担。
- 它产生的所有结论都能追溯到本地项目结构。
- 它的 A 阶段代码和数据结构不需要推翻，就能演进到 B 和 C。
