# Lessons

## 2026-05-13：任务收尾说明必须产品化

用户反馈：每次完成任务后，如果只解释代码、测试和内部状态，会跟不上当前产品开发进度。

后续规则：

- 每次完成一轮开发，先用产品语言说明“这轮对用户体验/产品流程改变了什么”。
- 必须明确页面入口：用户打开哪个 URL、点击哪个导航、看哪个面板、哪个按钮能验证。
- 剩余风险要写成产品风险，而不只是工程风险。例如“还不能写回正文”“还没有 docx 导出预检”“本地验收产物未决定是否进入 fixture”。
- 下一步计划要说明为什么是下一步，以及它在研究生命周期中的位置。
- 技术细节、测试命令和文件路径放在后面，作为证据，不作为唯一汇报主体。

推荐收尾结构：

1. 产品进展：这轮让用户现在可以做什么。
2. 你可以怎么验收：页面入口、点击路径、应看到的状态。
3. 行为覆盖：对应 BDD 行为。
4. 测试覆盖：命令和结果。
5. 实现范围：关键文件和接口。
6. 剩余风险：产品风险优先，工程风险其次。
7. 下一步计划：下一轮要做什么，以及为什么。
