## 1. 核心判据：多 Agent 何时真的优于单 Agent（10.2）

**唯一实质判据：** 协作过程是否引入了 **单个 Agent 在生成时无法获得的新信息**？

| 协作模式 | 是否引入新信息 | 效果（书中结论） |
|----------|----------------|------------------|
| 同一模型自我审查（再读自己的输出） | 否 | 通常无效甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 等计算量下 ≈ 单 Agent |
| Reviewer 用 **测试执行结果** 审代码 | 是（执行反馈） | 显著提升 |
| Reviewer 用 **渲染截图** 审前端/PPT | 是（视觉反馈） | 显著提升 |
| Reviewer 用 **外部工具** 验证事实 | 是（工具反馈） | 显著提升 |

**证据链（书内引用）：**

- RLEF：执行反馈 RL 远超独立多次采样。
- WebGen-Agent：视觉反馈脚手架使基准接近翻倍。
- Huang et al. ICLR 2024：无外部反馈的 self-correct 准确率可 **下降**。
- TACL 2024 综述：无可靠外部反馈时，纯自我纠正几乎不起作用。
- CRITIC：去掉工具验证后，大部分提升消失。
- Tran & Kiela 2026：等 thinking token 预算下，多跳推理上单 Agent 可 ≥ 多 Agent（辩论式串行传中间结论受数据处理不等式约束；**不**否定独立采样聚合或生成-验证难度不对称分工）。

**对研究/实证论文的直接含义：**

- 「审稿人 persona 再读一遍正文」= 剧场，不算 H7 增益。
- 真增益必须来自：**回归/估计日志、表哈希、claim↔table 对齐、REPRO 退出码、文献检索结果、独立 process 的审阅上下文**。
- Anthropic 多 Agent 研究系统：token ≈ 普通对话 **15×**，且 token 用量可解释约 **80%** 性能差 → 收益必须覆盖数量级开销，否则调好的单 Agent 更划算。

**步骤预算：** 单纯加步数不保证更好；需 **预算感知**（先广后窄）。Manager 应按子任务复杂度 **动态分配步数/token**，并要求子 Agent「规划→实现→测试→改进」，而非一头干。

## 2. 两个架构维度（10.1）

### 2.1 维度一：上下文是否共享

| | 共享上下文（线程式） | 不共享上下文（进程式） |
|--|----------------------|------------------------|
| 协调 | 隐式：继承完整轨迹 | 显式：文件 / 消息 / 工具参数 |
| 子任务数 | 少（2–3 角色） | 多、可并行 |
| 窗口 | 单窗够用 | 单窗装不下 |
| 并行 | 串行接棒为主 | 可大规模并行 |
| 信息隔离 | 不需要 | 需要（如安全审不应见原始思考） |
| 成本 | 单条轨迹累积 | 总 token 常高数倍到数量级 |
| 经验法则 | 累计上下文将超窗 **50%** → 不共享；信息零损耗是硬约束 → 共享 | |

**常见折中：** 前几个阶段共享，饱和后切 **不共享 + 显式 handoff**。

**通信机制 = IPC 两大范式：**

1. **共享文件系统**（共享内存）
2. **消息传递：** 工具调用参数（同步） / **消息总线**（异步）

书中引用 Go 箴言：不要通过共享内存来通信，而要通过通信来共享内存——共享快但并发隐患；消息多编排但归属清晰。

### 2.2 维度二：协作拓扑（不共享上下文下展开）

概念上 2×3 矩阵；**共享上下文一行拓扑多退化为角色切换序列**，故重点展开不共享的三格：

| 拓扑 | 别名 | 形态 | 适用 |
|------|------|------|------|
| 对等协作 | Peer | 2–3 Agent 迭代互馈 | 原型快、过早终止、提议者-审核者 |
| 管理者 | Orchestration | Manager 规划调度 + 子 Agent | ≥5 子任务、依赖复杂、动态调度 |
| 去中心化 | Decentralized / choreography | 对等移交、无中心控制 | 固定流水线 SOP、handoff 网络 |

**Graph Engineering（2026 流行名）：** 节点=Agent/程序/人，边=依赖/条件路由/失败去向；书用更稳术语「协作拓扑 / 编排」。

**OS 对照（表 10-3，工程必背）：**

| 操作系统 | 多 Agent |
|----------|----------|
| 程序 | 静态前缀（系统提示 + 工具定义） |
| 进程内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| fork / kill / ps | spawn_subagent / cancel_subagent / list_agents |
| 退出码 | 子 Agent **结构化摘要** |
| 共享内存 / 消息 | 共享文件系统 / 消息总线 |

**唯一失效点：** 进程传字节保真；Agent 传 **语义**，每次转述可失真 → 见失败模式「错误级联放大」。

## 3. 共享上下文模式（10.3）— 可用但非「真 multi-agent 进程」

### 3.1 多阶段角色转换

- 同一会话：换 **系统提示 + 工具集**，历史连续。
- 书承认：从进程看是「同一内存换代码段」；仍纳入框架是因为 **阶段边界 = 质量门**，身份可独立打磨。
- 例（实验 10-1）：需求澄清 → 实现 → 审查；阶段完成靠专用工具（`complete_*` / `submit_for_review` / `approve_code`），审查可 `request_revision` 回退。

### 3.2 跨领域 transfer（实验 10-2）

- 角色：triage / research / coding / data_analysis / writing。
- `transfer_to_agent(target, reason)`：保存历史 → 加载目标提示与工具 → 继续。
- 要防 **角色循环切换**。

**对实证环：** 10 步线性 pipeline 的「换 step 提示词」≈ 共享上下文角色转换；**不等于** H7 独立 IO。H7 要求至少数据平面 + 控制平面上的进程式隔离。

## 4. 不共享上下文：数据平面 + 控制平面（10.4.1–10.4.2）

### 4.1 虚拟文件系统四区（表 10-4）

| 区域 | 路径意象 | 可见性 | 生命周期 | 并发 |
|------|----------|--------|----------|------|
| Scratchpad | `/scratch/<id>` | 仅该 Agent | 随实例销毁 | 不需要 |
| Shared Workspace | `/workspace/shared` | 协作 Agent + 用户 | 随任务持久 | **乐观锁 / worktree** |
| Mounted external | `/mnt/gdrive` 等 | 外部授权 | 外部决定 | 外部负责；多为只读 |
| Built-in | `/skills` | 全局只读 | 跨会话稳定 | 不需要 |

**原则：** 默认隔离，共享须显式；子 Agent **试错留 scratch，只把终产物提交 shared**；Agent 间传 **路径字符串**，不把全文塞进上下文。

### 4.2 控制平面四项能力

1. **消息传递**  
   - 少 Agent：点对点。  
   - 多 Agent 异步：消息总线 + 结构化信封（sender, target, type, JSON body）。  
   - 类型例：`task_assigned` / `status_update` / `result` / `terminate`。

2. **状态查询（易被低估）**  
   - 拉取式 `get_status` 价值有限；更自然：  
     - 消息问答 / 主动 `status_update`；  
     - **轨迹 JSONL 持久化**（读「对方内存」但不耗对方上下文）；  
     - 约定 **`progress.md`**（轻量清单 + 最后修改时间做卡住检测）。  
   - 统一状态词：执行中 / 需要输入 / 已完成 / 失败（与 A2A 任务生命周期一致）。

3. **执行终止**  
   - 优雅 terminate（安全点清理 + ack）vs 强制 kill。  
   - 级联：父取消 → 子全部取消（Go context 模型）；长期后台用新生命周期树（nohup）。  
   - 竞态：多子同时成功 → 锁 / 幂等只结算一次。

4. **资源与调度**  
   - 稀缺：token、资金、并发额度。  
   - 启动时设步数/token 预算；强弱模型分流；并发上限；抢占。

**恢复 / 副作用契约：** 轨迹 + 检查点可重建会话；有外部副作用的工具须 **幂等键 + 客户端操作 ID**，崩溃后先查真实状态再决定重试 vs 人工对账（WAL 思想）。

## 5. 三种拓扑详解（研究 Agent 映射）

### 5.1 对等协作 + 提议者-审核者（10.4.3）— 默认最小真 multi-agent

**解决过早终止三种形态：**

1. 偷懒式假完成（写完不跑测）  
2. 过早放弃（一条路不通就宣布办不成）  
3. 假成功（口头同意 ≠ 闭环落地）

**Loop 工程 / LoopX 协议（书中具体框架）：**

```text
LoopX 决策 → Agent 执行 → 独立验证器证明 → LoopX 提交
```

- 模型可提出「完成」，**不能批准自己的完成**。  
- 目标与边界、门禁与待办、证据与配额、移交包 落在 **与运行时解耦的持久控制面**。

**Proposer–Reviewer：**

- Reviewer 必须接触 **新信息**（测试、渲染、检索、claim audit），不是同文再读。  
- 双 Agent 拆上下文：Reviewer 只看当前版本 + 外部证据；Proposer 只累积 **结构化文本反馈** → 防截图/日志上下文爆炸。

**其他对等（研究场景慎用）：** Debate（等预算下学术争议大）、Brainstorm、Panel（跨学科互补）。

**实证论文映射：**

| 角色 | 职责 | 新信息 |
|------|------|--------|
| Proposer / Writer | 设计、估计规格、成文 | — |
| Reviewer / Auditor | claim audit、REPRO、质量门 | 表 hash、回归日志、文献检索 |
| （可选）Estimator | 独立 process 跑 Stata/Python | 估计 log、系数表文件 |

### 5.2 管理者模式（10.4.4）— 长环 / 多步实证

- Manager 把子 Agent **建模为工具**（spawn / send / cancel / list）。  
- 子 → Manager：**结构化摘要**（结论、关键发现、产物路径、问题），**非全量轨迹**。  
- **Plan-and-Act：** 弱规划者是系统瓶颈 → **最强模型 + 最好提示优先给 Manager**（与「审查者能力应与被审者相近」不冲突：那是审查场景）。

**顺序 vs 并行：**

- 顺序：依赖清晰（术语表 → 分章翻译 → 全文审校）。  
- 并行：消息总线 + 实时监控 + 级联终止（实验 10-6：10 站点搜人，命中即 terminate 其余；串行 ~5min → 并行 ~19s 量级）。

**书籍翻译实验（10-3）= 研究流水线原型：**

| Agent | 产物 | 上下文内容 |
|-------|------|------------|
| Glossary | `glossary.json` | 全书术语相关 |
| Translation ×N | `chapter_n.md` | 当前章 + 术语表 |
| Proofreading | `review_report.md` | 全文一致性 |
| Manager | 计划 + 文件索引 | **不装完整译文** |

**产品化实例「灵台」：** 主器灵=Manager；分神=短时并行子 Agent（结论回传即弃）；分身=跨会话持久专家；知识私有文件 + 共享 Skills；上下文满则「凝蜕」写总结干净继续。

**实证论文映射（建议拓扑）：**

```text
                    Manager (PaperLoopOrchestrator)
                    最强模型 · 步数预算 · 门禁
           ┌───────────┼───────────┬────────────┐
           ▼           ▼           ▼            ▼
       Design/ID    Estimate     Write/Draft   Repro/Audit
       (子 Agent)   (子 Agent)   (子 Agent)    (独立 IO Reviewer)
           │           │           │            │
           └──── 产物路径进 shared workspace ───┘
                         ▲
                         │ 红灯 → Manager 回炉指定 step
                         │ 非「请人工确认」默认出口
```

### 5.3 去中心化 / Handoff（10.4.5）

**不共享下的移交包（三部分）：**

1. 任务描述 + 验收标准  
2. 已确认事实与约束  
3. 结构化产物 **路径引用**（不传全量轨迹）

**由伪到真：**

| 系统 | 实质 |
|------|------|
| MetaGPT | 控制流=固定 SOP 流水线；亮点=消息池+按角色订阅、标准化文档接口；Engineer 用 **可执行反馈** 自修 |
| AutoGen group chat | 共享对话 + **中心** GroupChatManager 选发言者；防 livelock 要终止条件 |
| OpenAI Swarm / Agents SDK | 真对等 handoff 网络；风险 **成环** → 移交次数上限 |

**Agent Swarm 一词两义：** (1) handoff 网络；(2) 大规模 **orchestrator-worker**（Kimi 百级子 Agent、Anthropic 研究系统、Manus Wide Research）。

### 5.4 A2A（10.4.6）— 跨组织才需要

- Agent Card / Task 状态机 / 不透明 Artifact 交换。  
- MCP = Agent↔工具；A2A = Agent↔Agent。  
- **同团队内部消息总线即可**，不必上 A2A。

## 6. 失败模式（10.5）— H7 必防

**MAST（Why Do Multi-Agent LLM Systems Fail?）：** 7 框架 ~150 轨迹 → 14 种失败，三大类：

1. 系统设计缺陷（接口不清、职责重叠、工具配错）  
2. Agent 间对齐失败（目标不一致、误解、逻辑矛盾）  
3. 任务验证缺失（声称完成 ≠ 真完成）

简单修补提升有限（例 ChatDev +15.6%）→ **架构级问题**。

**故障性质：** Agent 故障多是 **拜占庭式**（继续给出看似可信的错误），不是干净崩溃 → 需要独立冗余 + **确定性外部反馈**（测试/编译/DB/表哈希）作为「不会说谎」的部件。

### 6.1 共享文件系统并发

- 文件级 lost update → **乐观锁**（读时记 version，写时校验）。  
- 跨文件语义冲突 → 编排层禁止并行改依赖文件，或写后全局一致性检查。  
- Coding 主流：**worktree / 分支隔离**，冲突收敛到合并点（隔离优于共享后再协调）。

### 6.2 错误级联放大（传话游戏）

- 例：术语表把 reasoning 译成「推理」→ 多章翻译统一错误 → 校对见「一致」反而点赞。  
- Manager 若基于错误摘要调度，后续全盘建立在错误前提上。  
- **断链：** 独立 Reviewer（只看原始证据 vs 结论，不看前序思考）；确定性工具反馈；交叉验证。

### 6.3 循环失控（过早终止的对称面）

1. token 成本失控  
2. 理解债（交付快于人类理解）  
3. 认知投降（人放弃审查）  

解药：预算与终止条件、扎根真实观测的验证器、人做「循环工程师」而非只按开始键。

## 7. 生产持续进化（第 8 章）— H8 / evaluate→learn

### 7.1 总公式

```text
执行 → 记录轨迹 → 三层信号(结果/过程/质量)
     → 候选更新(知识 | 指令/Skill | 程序/Harness | 参数)
     → 验证·灰度·回滚 → 新稳定版进入下一轮
```

**保存经历 ≠ 学习。** 学习 = 评价 → 对照 → 归纳 → 验证后改后续行为。

**禁止：** 运行中未经验证反馈直接改参数 / 正式能力。

### 7.2 三层轨迹验证（图 8-2）

| 层 | 问什么 | 证据偏好 |
|----|--------|----------|
| 结果 | 是否真办成 | 测试、订单/金额、工具返回、**表 hash / REPRO 码** |
| 过程 | 是否以允许方式办成 | 政策、权限、动作序列、**无证据 claim 否决** |
| 质量 | 是否办得合适 | Rubric + LLM-as-Judge；**证据不足允许 uncertain** |

越下层越应代码/环境真值；标量总分不够 → **结构化诊断**（维度 pass/fail/uncertain + 证据位置 + 失败标签）。

**裁判与改写分离：** Judge 给评价；独立诊断/进化模块决定改哪里。

### 7.3 四种更新载体（按表示性质选，非单向阶梯）

| 载体 | 适合 | 优势 | 局限 |
|------|------|------|------|
| 经验知识库 | 事实、策略规律、例外 | 快、可追溯 | 依赖检索与正确应用 |
| Prompt / Skill | 可语言化原则 | 可解释、范围可控 | 膨胀、冲突、被忽略 |
| 程序 / Harness | 确定性流程与强约束 | 可测、稳、便宜 | 开发成本 |
| 参数 SFT/RL | 高维感知与隐式策略 | 泛化、推理开销低 | 更新与回归贵 |

**默认最小 diff；** 候选 + 来源 + 回归；通过才 canary，不直接覆盖稳定版。

### 7.4 在线 / 离线双循环（图 8-5）

- **在线：** 稳定版只干活 + 写不可变证据。  
- **离线：** 聚合诊断 → 候选 → 回归/安全 → 灰度 → 晋升。  
- **可信根不可被业务 Agent 修改：** 验证器、测试集、发布门槛、审计日志、稳定备份。

### 7.5 分层评估指标（表 8-3）

| 指标 | 问题 |
|------|------|
| 候选修改有效率 | 更新器是否提出有价值修改 |
| 产物激活率 | 任务 Agent 是否在正确场景加载新 Skill/工具 |
| 遵循成功率 | 激活后是否按新规则执行 |
| 留出任务增益 | held-out 是否真变好 |

拆开 **Harness-updating** vs **Harness-benefit**，避免「改对了但从未加载」误判。

长期五观察：回退、泛化、Token 效率、安全性、**长期工程质量**。

### 7.6 开放科研 / 自动科研边界（8.3.3）— 对本产品极关键

可验证闭环在 Coding / 业务状态变更上最稳；**开放式科研、战略、复杂设计** 则：

- 信号慢、答案不唯一、品味与长期价值难即时打分。  
- Harness 可能完整跑通却只稳定产出「像成果的东西」。

**Trehan & Chopra 四次自动科研尝试：** 三次实现/评估失败；问题三类：

1. **实现漂移**（难了就退回训练里熟悉但偏离假设的实现）  
2. **认识论过度乐观**（噪声当发现；阴性结果被忽略）  
3. **隐性判断力不足**（不知真基线、何异常值得追、何时放弃假设）

**必须改证据与监督结构（而非只换更会写论文的模型）：**

1. **结论与证据分离**（Chain-of-Evidence：引用/数字/方法/结论各挂来源；文稿只是证据图呈现）  
2. **保留负面结果**（失败实验、被拒候选、停止原因 = 与成功同等可检索；否则只学幸存偏差）  
3. **维护搜索多样性**（候选池按机制/假设异质保留，防收敛成易得分模板）  
4. **人在更高层介入**（定义问题、审评价标准、解释反常、决定停止）— 比逐步点批准更有价值  

### 7.7 安全三边界（8.3.4）

1. **证据与指令隔离**（网页/工具输出不可当指令进 Skill）  
2. **候选与正式能力隔离**  
3. **安全机制不可自我修改**

睡眠学习：空闲期整合/修剪/过期；容量约束；冲突用新证据替换旧规则。

## 8. 后记要点（生产哲学）

- 公式不变：`Agent = LLM + 上下文 + 工具`；生产竞争力在 **Model + Harness**。  
- **两朵乌云：** (1) 实时流式与环境交互；(2) 上岗后持续从成败中学习。  
- **大世界假设：** 公司/用户私有规则与边界会变 → 必须外围学习系统（记忆 + 第 8 章进化）。  
- Harness 不会被模型一次吃完：训练慢于业务；总有最新边界；新能力前沿仍不稳 → Harness **向新前沿迁移**。  
- 飞轮：真实任务 → Harness 补洞 → 信号回流训练 → 内化后删 Harness 层。

## 9. 对「全自动实证论文工作台」的验收映射

对照 `docs/BOOK_HARNESS.md` 与 structure-audit H7/H8：

| 书中原则 | 产品必须看见的行为 | 反模式 |
|----------|-------------------|--------|
| 新信息判据 | Reviewer 读估计 log / 表 / REPRO / 检索，而非再读草稿 | 多 persona 同窗辩论 |
| 不共享 + 路径 IO | 独立 process/workspace；产物路径进 shared | markdown 人设串台 |
| 子 Agent 返回摘要 | Manager 只持计划+索引+门禁状态 | Manager 上下文塞全文轨迹 |
| Loop 验证器判停 | quality/claim/REPRO 红灯 → 回炉；绿才 package | 模型自称 done；红灯仍 completed |
| 三层验证 | 结果（可复现）+ 过程（无捏造）+ 质量（Rubric） | 单一满意度/总分 |
| 在线/离线双环 | run 不可变轨迹；learn 离线写 Skill/Harness 候选 | 运行中直接改正式提示 |
| 开放科研边界 | 阴性结果入证据图；claim 挂来源；人定题/验收 | 噪声当发现；只留幸存路径 |
| 成本意识 | multi-agent 只在增益 > 数倍 token 时上 | 默认 10 个角色 |

**建议落地顺序（与书一致，复杂度递增）：**

1. 单 Agent + 确定性验证器 + 停止条件（Loop 工程最小集）  
2. Proposer–Reviewer 独立 IO（最小真 H7）  
3. Manager + 步数预算 + 文件索引（长 10 步环）  
4. 离线 evaluate→learn 写回 Skill/程序（H8）  
5. 仅当并行收益明确时再上总线 / 级联终止 / 大规模 swarm

## 11. 一页结论（给 structure-audit）

```text
真 multi-agent = 独立上下文/进程 + 显式数据平面(文件路径) + 控制平面(消息/终止/预算)
                 + 协作必须引入「生成时没有的」外部证据
假 multi-agent = 同窗换人设 / 同文辩论 / 自审自称完成

生产 research agent = 在线只记不可变轨迹
                      离线三层验 → 最小 diff 候选 → 回归/灰度/回滚
                      开放科研额外：证据图、阴性结果、多样候选、人定高层标准
```

**与 Continuous Empirical Loop 对齐句：**

> design → estimate → write → reproduce → revise，闸门内 ReAct；红灯触发纠正与回炉，不触发签到台；完成 = 可打开论文 + 可复现（或诚实降级）+ claim 可追溯。
