# 06 作品集叙事

## 项目标题

本地 AI 实证研究 OS：一个面向实证论文写作的可审计 Agent 工作台

## 作品集一句话

我设计并推动了一个本地优先的 AI 实证研究工作台，把实证论文从题目、数据、变量、方法、执行、写作到复现的流程拆成可审计的 Agent 任务队列，让用户在 AI 协助下仍然保留研究判断权。

## 背景问题

很多学生和研究者已经开始使用 AI 写论文，但最大问题不是 AI 不会写，而是 AI 太容易写出“像论文但缺证据”的文本。

传统实证研究还面临另一个问题：数据、代码、结果、文献和论文草稿分散在不同工具里。做久了以后，用户很难复盘：

- 这个变量为什么这样选？
- 这个系数来自哪个脚本？
- 这段结论有没有真实表格支撑？
- 这篇文献是否真的存在？
- 哪些内容只是草稿，哪些可以进入正式稿？

## 我的产品洞察

AI 实证研究产品不能只做“论文生成器”。它应该先做“研究操作系统”：

- 把研究流程拆开。
- 把 Agent 分工可视化。
- 把证据等级展示出来。
- 把人工确认点放在关键决策前。
- 把草稿层和正式层分开。

这样用户既能利用 AI 提高效率，又不会失去对研究质量的控制。

## 目标用户

第一版用户是做实证论文的学生、RA、初级研究者，以及项目作者本人。

他们的共同问题是：

- 有题目，但不知道怎么拆成可执行任务。
- 有数据，但不知道变量角色是否合理。
- 有 AI，但不知道生成内容是否可信。
- 有很多中间产物，但缺少复盘和审计路径。

## 核心方案

产品采用“题目优先 + Agent 任务队列 + 证据门禁”的结构。

用户输入题目后，系统不会直接写论文，而是先生成：

- 研究任务书。
- 数据与变量候选。
- 方法设计。
- 执行计划。
- Agent 分工。
- 证据缺口。
- 草稿边界。
- 审阅与导出预检。

每一步都显示状态、产物路径和人工确认点。

## 关键设计取舍

### 取舍 1：先做本地版

原因：目标用户第一阶段是本人和少数熟人。本地版能更快接入真实数据、真实日志和本地模型，验证研究工作流是否成立。

### 取舍 2：不做一键正式论文

原因：AI 可以生成草稿，但正式论文必须由证据、方法和引用共同支撑。产品先保证证据可信，再追求写作完整度。

### 取舍 3：主屏少展示，细节按需展开

原因：实证研究信息量很大，如果一开始铺满日志、队列、方法树和证据，会让用户失去方向。主屏只服务当前决策，细节进入 Inspector 或 Drawer。

### 取舍 4：引入正式层写回审批

原因：草稿可以快速迭代，但正式层必须安全。所有正式稿、正式变量角色、正式方法设计和最终导出包都需要人工确认。

## 当前成果

当前项目已经形成：

- CLI-first 工作流。
- 中文 8 阶段 run 目录。
- Agent Queue 和 stage 产物结构。
- 变量、方法、文献、写作、评审、正式写回的多阶段门禁。
- 本地数据和证据状态的基础机制。
- React / Web 工作台的多轮设计探索。

## 当前不足

这个项目还没有完全产品化：

- 需要固定一个 demo 案例。
- 需要把前端体验收束到一个清晰主路径。
- 需要稳定展示 LLM Supervisor 的真实介入。
- 需要把 Evidence Registry 和论文正文绑定得更硬。
- 需要把当前大量开发记录整理成作品集案例页。

## 作品集展示结构

面试中可以这样讲：

1. 我观察到 AI 论文生成的核心风险不是不会写，而是证据不可追。
2. 我定义了一个本地 AI 实证研究 OS，而不是普通论文生成器。
3. 我把研究流程拆成 8 个阶段和多个 Agent 角色。
4. 我设计了草稿层、审阅层、正式层，避免 AI 静默覆盖正式成果。
5. 我用 CLI 和本地文件系统先跑通工作流，再逐步接 Web UI。
6. 我用真实 run、测试、文档和审计产物验证产品路径。
7. 下一步是固定 demo 案例、提升 UI 可理解性、接入更稳定的真实统计执行和 LLM Supervisor。
