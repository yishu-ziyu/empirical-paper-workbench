# 08 Draft-first 交付标准

## 固定结论

第一版产品的用户体验必须围绕一个首交付物组织：

```text
paper_draft.pdf / paper_draft.docx
```

这是用户最先理解、最关心、最容易判断价值的产物。审计报告、证据账本、问题清单和运行日志都是支撑物，不能反过来成为第一屏的主产物。

## 产品承诺

正向承诺是：

```text
一键生成可审计的论文初稿。
```

它不是无证据的论文代写器。系统必须先判断题目、数据、变量、方法和执行证据是否能支撑成稿。

## 两条输出分支

### 成功分支

当数据、字段、模型和执行结果都通过门禁时，系统输出完整论文初稿：

- `paper_draft.pdf`
- `paper_draft.docx`
- `paper_draft.md` 或 `paper_draft.tex`
- 表格和图形
- 可复现运行清单
- 证据审计报告
- 答辩问题或风险清单

CHARLS DID 跑通样例属于成功分支：它证明系统可以在真实数据、真实脚本和真实模型链路成立时生成质量可接受的完整初稿。

### 阻断分支

当关键字段、文献、模型前提或执行结果不足时，系统仍然输出用户可读的半成品论文：

- `paper_draft.pdf` 或 `paper_draft.docx`
- 能写的章节先写
- 不能写的段落用红标或明确占位标出
- 同步输出 `issue_list.md`
- 同步输出 `audit_report.md`

父母教育工资当前 Demo 线属于阻断分支：题目成立，但父母教育字段尚未绑定，因此不能伪装成完整论文。

## 用户体验规则

- 用户入口和最终验收都以 `paper_draft.pdf / .docx` 为中心。
- 审计报告默认作为附件或右侧详情，不抢占主产物位置。
- 问题清单必须能解释为什么当前是完整初稿或半成品。
- 半成品不是失败页面；它是有价值的研究工作包。
- 任何完整初稿都必须能追到数据、变量、模型、结果和证据记录。

## 后续实现含义

后续 UI、API 和工作流阶段应围绕以下交付包设计：

```text
DraftPackage
├── paper_draft.pdf
├── paper_draft.docx
├── audit_report.md
├── issue_list.md
├── evidence_manifest.json
└── reproduction_manifest.json
```

第一优先级是让用户拿到可打开、可阅读、可修改的论文初稿文件；第二优先级才是让用户进入证据、日志和 Agent 细节。
